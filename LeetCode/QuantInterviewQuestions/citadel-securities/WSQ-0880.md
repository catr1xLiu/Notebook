> [!example] Question 880 · Citadel Securities
> ## Quant Developer Interview

How is std::map implemented internally?

[Source](https://www.thewallstreetquants.com/ebook#p=881)

> [!success]- Solution (Click to expand)
> `std::map` is typically implemented as a **balanced binary search tree**, almost always a **red–black tree** in mainstream standard library implementations.
>
> ## 1. What `std::map` stores
>
> A `std::map<Key, T>` stores elements of type
>
> $$
> \texttt{std::pair<const Key, T>}
> $$
>
> ordered by the key using a comparison object, by default
>
> $$
> \texttt{std::less<Key>}
> $$
>
> The ordering is not based on insertion order, nor on hashing; it is based on the tree order induced by the comparator.
>
> ## 2. Why a balanced tree is used
>
> The standard requires logarithmic-time complexity for key operations such as
>
> - insertion,
> - erasure,
> - lookup.
>
> A plain binary search tree can degrade to height
>
> $$
> O(n)
> $$
>
> in the worst case, so implementations use a self-balancing tree. A red–black tree guarantees height
>
> $$
> O(\log n)
> $$
>
> which gives
>
> $$
> O(\log n)
> $$
>
> time for search, insert, and erase.
>
> ## 3. Typical node structure
>
> A map node usually contains:
>
> - the stored value
>
> $$
> \texttt{pair<const Key, T>}
> $$
>
> - pointers to children,
> - a pointer to the parent,
> - a color bit for red–black balancing.
>
> Conceptually, a node looks like
>
> ```cpp
> struct node {
>     node* parent;
>     node* left;
>     node* right;
>     bool color; // red or black
>     std::pair<const Key, T> value;
> };
> ```
>
> Actual implementations may compress the color bit or use special sentinel nodes.
>
> ## 4. Red–black tree invariants
>
> A red–black tree maintains ordering plus balancing rules such as:
>
> 1. Every node is either red or black.
> 2. The root is black.
> 3. Red nodes do not have red children.
> 4. Every path from a node to a null leaf has the same number of black nodes.
>
> These constraints keep the tree height bounded by
>
> $$
> O(\log n)
> $$
>
> ## 5. How lookup works
>
> To find key $k$, the implementation starts at the root and repeatedly compares:
>
> - if $k$ is less than the current node’s key, go left;
> - if the current node’s key is less than $k$, go right;
> - otherwise the keys are equivalent, so the node is found.
>
> Because the tree height is
>
> $$
> O(\log n)
> $$
>
> lookup takes
>
> $$
> O(\log n)
> $$
>
> time.
>
> ## 6. How insertion works
>
> To insert a key:
>
> 1. Perform ordinary binary-search-tree insertion to find the proper leaf position.
> 2. Create a new node there.
> 3. Rebalance using recoloring and tree rotations.
>
> The rotations are local pointer rearrangements that preserve in-order key ordering while restoring red–black properties.
>
> Thus insertion remains
>
> $$
> O(\log n)
> $$
>
> ## 7. How erasure works
>
> Erasure is more involved:
>
> 1. Find the node.
> 2. If it has two children, replace it with its in-order successor or predecessor.
> 3. Remove a node with at most one child.
> 4. Rebalance using red–black deletion fix-up logic.
>
> This also runs in
>
> $$
> O(\log n)
> $$
>
> time.
>
> ## 8. Why iteration is ordered
>
> An in-order traversal of a binary search tree visits keys in sorted order. Therefore iterating through `std::map` yields elements in ascending order according to the comparator.
>
> This is why:
>
> - `begin()` points to the smallest key,
> - incrementing an iterator moves to the next larger key,
> - decrementing moves to the previous key.
>
> Implementations usually support this efficiently by storing parent pointers and often a special header/sentinel node.
>
> ## 9. Typical use of a header node
>
> Many implementations keep a special sentinel/header node that stores links such as:
>
> - root,
> - leftmost node,
> - rightmost node.
>
> This makes operations like
>
> - `begin()`,
> - `end()`,
> - finding minimum/maximum,
>
> more convenient and efficient.
>
> Often:
>
> - `header.parent` points to the root,
> - `header.left` points to the smallest element,
> - `header.right` points to the largest element.
>
> Then `end()` can be represented by an iterator to this header node.
>
> ## 10. Iterator stability
>
> Because elements live in separate tree nodes, insertions and most other structural changes do not move existing elements in memory. Hence `std::map` provides strong iterator/reference stability:
>
> - inserting does **not** invalidate iterators or references to existing elements,
> - erasing invalidates only iterators/references to the erased element.
>
> This behavior is a natural consequence of node-based tree storage.
>
> ## 11. Memory characteristics
>
> Compared with a contiguous container, a tree-based map has higher overhead:
>
> - one allocation per node,
> - multiple pointers per node,
> - balancing metadata,
> - poorer cache locality.
>
> So while asymptotic complexity is good, constants are larger than for array-based structures.
>
> ## 12. Why not a hash table?
>
> `std::unordered_map` is the hash-table-based associative container. In contrast, `std::map` is chosen when one wants:
>
> - sorted order,
> - predecessor/successor operations,
> - range queries such as `lower_bound` and `upper_bound`,
> - guaranteed worst-case logarithmic behavior.
>
> A hash table does not naturally support ordered traversal or range search.
>
> ## 13. Standard versus implementation detail
>
> The C++ standard does **not** require `std::map` to be a red–black tree specifically. It requires the observable behavior and complexity guarantees of an ordered associative container. However, red–black trees are the conventional implementation because they fit those requirements well.
>
> ## Conclusion
>
> Internally, `std::map` is almost always a **node-based red–black tree** storing elements of type
>
> $$
> \texttt{pair<const Key, T>}
> $$
>
> in sorted key order. Each node holds the value plus tree links and balancing information. Search, insertion, and erasure all take
>
> $$
> O(\log n)
> $$
>
> time, iteration is in sorted order, and iterators remain stable except for erased elements.
