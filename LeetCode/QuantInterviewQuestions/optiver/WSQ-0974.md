> [!example] Question 974 · Optiver
> ## Senior Software Developer Interview

Given an exchange feed that provides up to five rows of depth information per second (five price points and their respective quantities, for both buy and sell sides of a specific stock), design and implement a more efficient solution on the server so that clients are only sent updates for price points whose quantity has changed, rather than sending all the data every time.

[Source](https://www.thewallstreetquants.com/ebook#p=975)

> [!success]- Solution (Click to expand)
> ## Solution
>
> We are given a market data server that receives, once per second, up to $5$ levels of book depth for each side of a single instrument:
>
> - buy side: up to $5$ price levels with quantities,
> - sell side: up to $5$ price levels with quantities,
>
> already sorted by price.
>
> The current server republishes the entire snapshot to all clients every time. The goal is to send only meaningful changes: if a price level has not changed in quantity, clients should not be notified unnecessarily.
>
> ---
>
> ## 1. Clarifying the requirement
>
> A precise interpretation is needed.
>
> Each update from the exchange is a **snapshot** of the top $5$ levels per side, not an incremental feed. Therefore, to reduce bandwidth, the server should transform snapshots into **deltas** before sending to clients.
>
> A client must still be able to reconstruct the current book state from:
>
> - an initial full snapshot, and
> - subsequent incremental updates.
>
> A “change” at a level can occur in several ways:
>
> 1. a price level remains present and its quantity changes;
> 2. a price level disappears;
> 3. a new price level appears;
> 4. the ordering shifts because a better price enters or an old one drops out.
>
> Therefore comparing only by array position is incorrect. Comparison must be done by **price level**, separately for each side.
>
> ---
>
> ## 2. Data model
>
> Represent each side of the book as a mapping
>
> $$
> \text{price} \mapsto \text{quantity}
> $$
>
> for the current top $5$ levels.
>
> For example:
>
> - bids: descending by price,
> - asks: ascending by price.
>
> A snapshot may be stored as:
>
> $$
> \text{BookSnapshot} =
> \{
> \text{bids}: \{p \to q\},
> \text{asks}: \{p \to q\}
> \}
> $$
>
> where the number of entries on each side is at most $5$.
>
> To preserve display order for clients, the server can also keep the ordered list of levels, but for change detection the map representation is sufficient.
>
> ---
>
> ## 3. Incremental update format
>
> Send clients only the set of changes since the previous snapshot.
>
> For each side, define update events of the form:
>
> - **upsert**: price level exists with new quantity,
> - **remove**: price level no longer exists.
>
> A compact delta can be:
>
> $$
> \text{Delta} =
> \{
> \text{sequenceNumber},
> \text{bidChanges}: [(\text{price}, \text{qty or remove})],
> \text{askChanges}: [(\text{price}, \text{qty or remove})]
> \}
> $$
>
> Examples:
>
> - if bid at price $100$ changes from quantity $20$ to $25$, send $(100, 25)$;
> - if ask at price $103$ disappears, send $(103, \text{remove})$;
> - if new best bid at $101$ quantity $10$ appears, send $(101, 10)$.
>
> A quantity of $0$ may be used instead of an explicit remove marker, if the protocol allows it.
>
> ---
>
> ## 4. Core algorithm
>
> Let:
>
> - $\text{prev}$ be the previous snapshot,
> - $\text{curr}$ be the newly received snapshot.
>
> For one side of the book, let:
>
> - $\text{prevMap}$ be the old price-to-quantity map,
> - $\text{currMap}$ be the new price-to-quantity map.
>
> The delta is computed in two passes.
>
> ### Step 1: detect additions and quantity changes
>
> For each $(p, q)$ in $\text{currMap}$:
>
> - if $p \notin \text{prevMap}$, emit **upsert** $(p, q)$;
> - else if $\text{prevMap}[p] \ne q$, emit **upsert** $(p, q)$;
> - else emit nothing.
>
> ### Step 2: detect removals
>
> For each price $p$ in $\text{prevMap}$:
>
> - if $p \notin \text{currMap}$, emit **remove** $(p)$.
>
> This is done independently for bids and asks.
>
> Finally replace $\text{prev} \leftarrow \text{curr}$.
>
> ---
>
> ## 5. Why position-based comparison fails
>
> Suppose the old bids are:
>
> $$
> [(100, 10), (99, 8), (98, 5)]
> $$
>
> and the new bids are:
>
> $$
> [(101, 4), (100, 10), (99, 8), (98, 5)]
> $$
>
> A position-based comparison would claim that every row changed.
>
> In reality, only one new level was added:
>
> $$
> (101, 4)
> $$
>
> and perhaps the former fifth level dropped off if the depth limit was exceeded.
>
> Therefore the correct comparison key is **price**, not index.
>
> ---
>
> ## 6. Example
>
> Assume previous snapshot is:
>
> ### Bids
> $$
> (100, 10),\ (99, 20),\ (98, 15)
> $$
>
> ### Asks
> $$
> (101, 12),\ (102, 18),\ (103, 25)
> $$
>
> New snapshot:
>
> ### Bids
> $$
> (100, 10),\ (99, 22),\ (97, 9)
> $$
>
> ### Asks
> $$
> (101, 12),\ (102, 18),\ (104, 30)
> $$
>
> Now compare.
>
> ### Bid side
>
> - $(100, 10)$ unchanged $\Rightarrow$ send nothing.
> - $(99, 20) \to (99, 22)$ changed quantity $\Rightarrow$ send $(99, 22)$.
> - $(97, 9)$ is new $\Rightarrow$ send $(97, 9)$.
> - $(98, 15)$ disappeared $\Rightarrow$ send remove for $98$.
>
> ### Ask side
>
> - $(101, 12)$ unchanged.
> - $(102, 18)$ unchanged.
> - $(104, 30)$ is new $\Rightarrow$ send $(104, 30)$.
> - $(103, 25)$ disappeared $\Rightarrow$ send remove for $103$.
>
> So the outgoing delta is:
>
> - bids: update $(99, 22)$, add $(97, 9)$, remove $98$;
> - asks: add $(104, 30)$, remove $103$.
>
> ---
>
> ## 7. Complexity
>
> Each side contains at most $5$ levels, so the work per snapshot is tiny.
>
> More generally, if there are $n$ levels per side, then using hash maps:
>
> - build current map: $O(n)$,
> - compare maps: $O(n)$.
>
> Thus total time is
>
> $$
> O(n)
> $$
>
> per update, with
>
> $$
> O(n)
> $$
>
> space for storing the previous snapshot.
>
> Since here $n \le 5$, performance is trivial even with many instruments.
>
> ---
>
> ## 8. Server design
>
> A practical design is:
>
> 1. **Exchange handler** receives raw snapshots.
> 2. **Book state cache** stores the latest snapshot per instrument.
> 3. **Delta generator** computes differences from the previous snapshot.
> 4. **Publisher** sends:
>    - full snapshot to newly connected clients,
>    - deltas to subscribed clients afterward.
>
> ### Important detail: initial synchronization
>
> A client cannot apply deltas unless it has a known starting state. Therefore:
>
> - on subscription, send a full snapshot with sequence number $s$;
> - then send all later deltas with sequence numbers $> s$.
>
> ### Sequence numbers
>
> Every published message should carry a monotonically increasing sequence number:
>
> $$
> 1, 2, 3, \dots
> $$
>
> This allows clients to detect missed messages. If a client detects a gap, it should request or wait for a fresh full snapshot.
>
> ---
>
> ## 9. Edge cases
>
> ### 9.1 Empty side
>
> If one side becomes empty, every previously existing price on that side must be removed.
>
> ### 9.2 Duplicate prices
>
> Within one side of a properly formed depth snapshot, prices should be unique. If duplicates appear, the server should reject or normalize the snapshot.
>
> ### 9.3 Quantity zero
>
> If the exchange includes a level with quantity $0$, treat it as absent unless the protocol explicitly defines otherwise.
>
> ### 9.4 Top-$5$ truncation
>
> Because only the top $5$ levels are visible, a level may disappear from the snapshot not because it vanished from the true book, but because it moved outside the visible depth. From the client’s perspective this still means it must be removed from the client’s maintained top-$5$ state. So removal is still correct.
>

> ## 10. Whiteboard-quality pseudocode
>
> ```text
> struct Level {
>     price
>     qty
> }
>
> struct Snapshot {
>     bids: list<Level>   // sorted descending
>     asks: list<Level>   // sorted ascending
> }
>
> struct Change {
>     side      // BID or ASK
>     price
>     qty
>     isRemove
> }
>
> function buildMap(levels):
>     map = {}
>     for level in levels:
>         map[level.price] = level.qty
>     return map
>
> function diffSide(prevLevels, currLevels, side):
>     prevMap = buildMap(prevLevels)
>     currMap = buildMap(currLevels)
>
>     changes = []
>
>     for (price, qty) in currMap:
>         if price not in prevMap:
>             changes.append(Change(side, price, qty, false))
>         else if prevMap[price] != qty:
>             changes.append(Change(side, price, qty, false))
>
>     for (price, qty) in prevMap:
>         if price not in currMap:
>             changes.append(Change(side, price, 0, true))
>
>     return changes
>
> function diffSnapshot(prevSnapshot, currSnapshot):
>     changes = []
>     changes += diffSide(prevSnapshot.bids, currSnapshot.bids, BID)
>     changes += diffSide(prevSnapshot.asks, currSnapshot.asks, ASK)
>     return changes
> ```
>
> ---
>
> ## 11. Possible optimization
>
> Since there are only $5$ levels, one could compare sorted arrays directly without hash maps. However, map-based comparison is clearer and more robust because identity is by price, not by position.
>
> If absolute efficiency were required for very large numbers of instruments, one could store each side in a small fixed-size array and perform a linear merge-like comparison of two sorted lists in $O(n)$ time without hashing.
>
> For example, because both old and new levels are sorted by price, bids and asks can be diffed with two pointers:
>
> - if prices match, compare quantities;
> - if one price is better than the other, it is an insertion or deletion depending on which side it belongs to.
>
> This avoids hash allocations, but the conceptual solution remains the same.
>
> ---
>
> ## 12. Final answer
>
> The correct solution is to maintain the previous top-of-book snapshot for each instrument, compare each new snapshot against it by **price level** on each side, and publish only the delta:
>
> - send an update when a price level is new or its quantity changed;
> - send a removal when a previously visible price level is no longer present;
> - send nothing for unchanged levels.
>
> Clients receive:
>
> 1. an initial full snapshot,
> 2. then sequenced incremental deltas.
>
> This reduces unnecessary traffic while allowing clients to reconstruct the exact current top-$5$ bid and ask book.
