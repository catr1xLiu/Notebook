> [!example] Question 952 · Optiver
> ## Internship Interview

Given a stream of stock price updates for both buy and sell orders, develop an efficient method to send and process the data to reduce overhead. Discuss considerations for using TCP versus UDP for transmitting this data.

[Source](https://www.thewallstreetquants.com/ebook#p=953)

> [!success]- Solution (Click to expand)
> ## Efficient Market Data Update Design
>
> To reduce overhead in a stream of stock price updates for both buy and sell sides, the key idea is to avoid sending the full state on every update. Instead, transmit only the information that changed, encode it compactly, and choose a transport protocol that matches the reliability and latency requirements.
>
> ---
>
> ## 1. Problem with Sending Full Updates
>
> Suppose each update contains the full current state:
>
> - symbol
> - best bid price and size
> - best ask price and size
> - timestamp
> - sequence metadata
>
> If this entire structure is sent for every change, then:
>
> 1. many fields are repeated unnecessarily,
> 2. bandwidth usage grows quickly with update frequency,
> 3. parsing cost increases,
> 4. latency may worsen due to larger messages.
>
> A more efficient design is to send an initial snapshot and then incremental updates.
>
> ---
>
> ## 2. Recommended Data Model
>
> ### 2.1 Initial Snapshot + Incremental Deltas
>
> Send:
>
> 1. **Snapshot**: the complete current state once, when a client subscribes.
> 2. **Delta updates**: only the fields that changed after that.
>
> For example, if only the bid price changes, send only:
>
> - instrument identifier
> - field identifier for bid price
> - new value
> - sequence number
>
> This avoids retransmitting unchanged ask information.
>
> ---
>
> ## 3. Compact Message Format
>
> A practical message can include:
>
> - **instrument id** instead of full symbol string
> - **bitmask of changed fields**
> - **delta-encoded values** where applicable
> - **sequence number**
> - **timestamp**, possibly relative rather than absolute
>
> ### 3.1 Example Structure
>
> Let the current state for one instrument be:
>
> - bid price
> - bid size
> - ask price
> - ask size
>
> Assign a bitmask:
>
> - bit $0$: bid price changed
> - bit $1$: bid size changed
> - bit $2$: ask price changed
> - bit $3$: ask size changed
>
> Then a message may look conceptually like:
>
> $$
> (\text{seq}, \text{instrument\_id}, \text{change\_mask}, \text{changed values})
> $$
>
> If only bid price and ask size changed, then:
>
> $$
> \text{change\_mask} = 1001_2
> $$
>
> and only those two values are included.
>
> This reduces both wire size and decoding effort.
>
> ---
>
> ## 4. Additional Compression Techniques
>
> ### 4.1 Integer Encoding Instead of Floating Point
>
> Represent prices in ticks or fixed-point integers rather than strings or floating-point values.
>
> For example, if the minimum tick is $0.01$, then:
>
> $$
> 123.45 \mapsto 12345
> $$
>
> This is smaller, faster to encode, and avoids precision issues.
>
> ### 4.2 Delta Encoding
>
> Instead of sending the full new price, send the change from the previous value:
>
> $$
> \Delta p = p_t - p_{t-1}
> $$
>
> If price movements are usually small, $\Delta p$ is small and can be encoded efficiently.
>
> Similarly, timestamps can be sent as:
>
> $$
> \Delta t = t_t - t_{t-1}
> $$
>
> ### 4.3 Batching
>
> If several updates occur within a very short interval, batch them into a single packet:
>
> $$
> (\text{packet header}, \text{update}_1, \text{update}_2, \dots, \text{update}_n)
> $$
>
> This amortizes header overhead from both the application protocol and the network stack.
>
> A trade-off exists:
>
> - larger batch $\Rightarrow$ less overhead
> - larger batch $\Rightarrow$ slightly higher latency
>
> Thus batching should be time-bounded, such as every $1$ to $5$ milliseconds, or size-bounded.
>
> ### 4.4 Binary Protocol Instead of Text
>
> Use a binary protocol rather than JSON, XML, or verbose text.
>
> Binary formats provide:
>
> - smaller payloads,
> - faster parsing,
> - predictable field sizes.
>
> For market data, this is usually preferable.
>
> ---
>
> ## 5. Sequence Numbers and Recovery
>
> Incremental feeds require a way to detect packet loss or missed updates. Add a monotonically increasing sequence number:
>
> $$
> s_1, s_2, s_3, \dots
> $$
>
> If a receiver observes:
>
> $$
> s_k, s_{k+2}
> $$
>
> then update $s_{k+1}$ is missing.
>
> The receiver can then:
>
> 1. request retransmission, or
> 2. request a fresh snapshot and resume from the latest sequence.
>
> This mechanism is essential, especially if unreliable transport is used.
>
> ---
>
> ## 6. Processing Efficiency on the Receiver
>
> To process updates efficiently:
>
> 1. maintain an in-memory state table keyed by instrument id,
> 2. decode the change mask,
> 3. update only modified fields,
> 4. apply updates in sequence order.
>
> If the local state for instrument $i$ is:
>
> $$
> S_i = (\text{bid\_price}, \text{bid\_size}, \text{ask\_price}, \text{ask\_size})
> $$
>
> and an update changes only bid size, then only that field is overwritten.
>
> This is much cheaper than reparsing and rebuilding the full object on every message.
>
> ---
>
> ## 7. TCP vs. UDP
>
> The choice between TCP and UDP depends on the desired balance among latency, reliability, ordering, and implementation complexity.
>
> ### 7.1 TCP
>
> TCP provides:
>
> - reliable delivery,
> - in-order delivery,
> - retransmission of lost packets,
> - built-in congestion control.
>
> #### Advantages
> - simpler application logic,
> - no need to implement loss recovery from scratch,
> - good when every update must be received correctly.
>
> #### Disadvantages
> - retransmissions can increase latency,
> - head-of-line blocking occurs: if one packet is lost, later packets are delayed until recovery,
> - can be inefficient for very high-rate real-time market data where freshness matters more than perfect completeness.
>
> TCP is appropriate when correctness and simplicity matter more than absolute lowest latency.
>
> ---
>
> ### 7.2 UDP
>
> UDP provides:
>
> - no built-in reliability,
> - no guaranteed ordering,
> - no retransmission,
> - low protocol overhead.
>
> #### Advantages
> - lower latency,
> - no head-of-line blocking,
> - suitable when the latest state is more important than old missed updates.
>
> #### Disadvantages
> - the application must handle:
>   - packet loss,
>   - reordering,
>   - duplication,
>   - recovery logic.
>
> UDP is often used for real-time market data dissemination because stale data is less valuable than current data. A missed update can be corrected by a later delta or by requesting a snapshot.
>
> ---
>
> ## 8. Practical Recommendation
>
> A common and effective architecture is:
>
> ### Option A: TCP Only
> Use TCP if:
>
> - update rates are moderate,
> - clients are few,
> - simplicity is important,
> - missing any update is unacceptable.
>
> ### Option B: UDP Multicast + TCP Recovery
> Use:
>
> - **UDP multicast** for high-rate real-time updates,
> - **TCP** for:
>   - initial snapshot,
>   - gap recovery,
>   - control messages.
>
> This is widely used in market data systems because it combines:
>
> - low-latency distribution via UDP,
> - reliable recovery via TCP.
>
> The workflow is:
>
> 1. client connects via TCP and obtains a snapshot,
> 2. client joins UDP stream for incremental updates,
> 3. client checks sequence numbers,
> 4. if a gap is detected, client requests retransmission or a new snapshot over TCP.
>
> This approach minimizes bandwidth and latency while preserving correctness.
>
> ---
>
> ## 9. Summary of the Efficient Design
>
> A more efficient way to send and process stock buy/sell updates is:
>
> 1. send one full snapshot initially,
> 2. send incremental delta updates thereafter,
> 3. identify instruments with compact numeric ids,
> 4. use a bitmask to indicate changed fields,
> 5. encode prices and sizes as integers,
> 6. optionally delta-encode values and timestamps,
> 7. batch multiple updates when acceptable,
> 8. use a binary protocol,
> 9. include sequence numbers for loss detection.
>
> For transport:
>
> - choose **TCP** for simplicity and guaranteed delivery,
> - choose **UDP** when low latency and freshness are more important than strict reliability,
> - for high-performance market data, the best design is often **UDP for streaming updates plus TCP for snapshot and recovery**.
>
> ## Final Answer
>
> The efficient solution is to replace full repeated buy/sell state messages with a **snapshot-plus-delta protocol**:
>
> $$
> (\text{seq}, \text{instrument\_id}, \text{change\_mask}, \text{changed values})
> $$
>
> using compact binary encoding, integer prices/sizes, optional delta compression, and bounded batching. On the receiver, maintain local state and apply only changed fields.
>
> For transport, use:
>
> - **TCP** if reliability and implementation simplicity are the priority,
> - **UDP** if minimal latency and real-time freshness are the priority,
> - ideally **UDP for live incremental updates and TCP for initial snapshot and recovery**, which gives the best trade-off for high-frequency stock price distribution.
