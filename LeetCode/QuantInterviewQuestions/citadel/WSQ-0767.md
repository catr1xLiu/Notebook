> ## Software Engineer Interview

Design a financial instrument trading system. How would you ensure atomicity, consistency, and other properties in the system?

> # Designing a Financial Instrument Trading System with ACID Guarantees
>
> A financial trading system must process orders with very low latency while preserving correctness under concurrency, failures, and partial network outages. The core requirement is that every state transition affecting money, positions, and risk must be reliable. This is naturally framed in terms of **atomicity, consistency, isolation, and durability**.
>
> ## 1. System goals
>
> A trading platform typically supports:
>
> - Order entry: market, limit, stop, cancel, amend
> - Matching and execution
> - Account balances and position management
> - Risk checks and margin enforcement
> - Market data dissemination
> - Clearing, settlement, and audit
> - Regulatory reporting
>
> The design must optimize for:
>
> - Low latency
> - High throughput
> - Deterministic processing
> - Fault tolerance
> - Strong auditability
> - Correctness of financial state
>
> ---
>
> ## 2. High-level architecture
>
> A practical architecture separates latency-sensitive components from state-management and reporting components.
>
> ### Core components
>
> 1. **API Gateway**
>    - Accepts client orders
>    - Authenticates users
>    - Applies rate limits
>    - Assigns idempotency keys
>
> 2. **Order Management System (OMS)**
>    - Validates orders
>    - Tracks order lifecycle
>    - Routes orders to the matching engine
>
> 3. **Risk Engine**
>    - Pre-trade checks:
>      - buying power
>      - position limits
>      - fat-finger checks
>      - margin sufficiency
>    - Post-trade risk updates
>
> 4. **Matching Engine**
>    - Maintains the order book for each instrument
>    - Matches buy/sell orders deterministically
>    - Produces execution events
>
> 5. **Ledger Service**
>    - Maintains cash balances, reserved funds, positions
>    - Uses double-entry accounting
>    - Acts as system of record for financial state
>
> 6. **Market Data Service**
>    - Publishes order book updates and trades
>
> 7. **Settlement/Clearing Service**
>    - Handles trade finalization and external clearing workflows
>
> 8. **Audit/Event Store**
>    - Persists immutable events for replay and compliance
>
> ---
>
> ## 3. Core data model
>
> The most important principle is to distinguish between:
>
> - **Commands**: requests such as “place order”
> - **Events**: facts such as “order accepted” or “trade executed”
> - **State**: balances, positions, open orders, order books
>
> ### Key entities
>
> - `Account`
> - `Instrument`
> - `Order`
> - `Execution`
> - `Position`
> - `CashBalance`
> - `Reservation` for held funds or securities
> - `LedgerEntry`
>
> ### Ledger model
>
> Use **double-entry accounting**. Every financial change is represented by entries whose net sum is zero.
>
> For example, if a buy trade is executed:
>
> - debit reserved cash
> - credit exchange payable
> - debit acquired security receivable
> - credit pending position adjustment
>
> This guarantees financial conservation and is central to consistency.
>
> ---
>
> ## 4. Transaction boundaries
>
> Not every operation in a distributed trading system should be wrapped in one global transaction. That would be too slow and fragile. Instead, define **local ACID boundaries** around critical state transitions.
>
> A sensible decomposition is:
>
> ### Transaction type A: Order acceptance
>
> Within one database transaction:
>
> - verify account exists and is active
> - verify order validity
> - reserve required funds or quantity
> - create order record
> - append `OrderAccepted` event
>
> If any step fails, the whole transaction rolls back.
>
> ### Transaction type B: Match execution
>
> Within one transaction, or within a single-threaded engine plus durable append:
>
> - consume resting order quantity
> - consume incoming order quantity
> - generate trade record
> - update order states
> - append `TradeExecuted` event
>
> ### Transaction type C: Post-trade ledger update
>
> Within one transaction:
>
> - update balances
> - update positions
> - release or reallocate reservations
> - write double-entry ledger records
> - mark settlement obligations
>
> These transaction scopes keep correctness while allowing horizontal scale.
>
> ---
>
> ## 5. Ensuring atomicity
>
> Atomicity means that a business operation either completes entirely or has no effect.
>
> ## 5.1 Local database transactions
>
> For operations inside one service boundary, use a relational database with transaction support:
>
> - PostgreSQL
> - Oracle
> - MySQL with proper transactional engine
>
> For example, on order placement:
>
> $$
> \text{reserve funds} \;\wedge\; \text{create order} \;\wedge\; \text{write event}
> $$
>
> must commit together.
>
> If one step fails, the transaction rolls back.
>
> ## 5.2 Outbox pattern
>
> A frequent problem is updating the database and publishing an event to a message broker. If done naively, one may succeed while the other fails.
>
> To avoid this, write the outgoing event into an **outbox table** in the same database transaction as the business update. Then a separate relay process publishes the event to Kafka or another broker.
>
> Thus:
>
> - database state change commits
> - outbox record commits with it
> - publisher retries until message is sent
>
> This guarantees atomic persistence of state and intent to publish.
>
> ## 5.3 Idempotency
>
> Clients may retry due to timeouts. The system must not create duplicate orders or duplicate trades.
>
> Assign each client request an idempotency key:
>
> - if unseen, process request
> - if repeated, return prior result
>
> This is essential for atomic behavior at the API level.
>
> ## 5.4 Sagas for distributed workflows
>
> Cross-service operations such as settlement or external clearing may not fit in one ACID transaction. In those cases use a **saga**:
>
> - break workflow into steps
> - each step commits locally
> - compensating actions undo prior effects if later steps fail
>
> For example:
>
> - reserve funds
> - accept order
> - route to venue
> - if venue rejects, release reservation
>
> This does not provide global atomic commit, but it provides controlled recovery semantics.
>
> ---
>
> ## 6. Ensuring consistency
>
> Consistency means all committed states satisfy business invariants.
>
> ## 6.1 Business invariants
>
> Examples include:
>
> - account cash cannot go below allowed margin threshold
> - position must reflect sum of executions
> - open order quantity cannot be negative
> - total debits equal total credits in ledger
> - reserved cash cannot exceed available cash
> - matched quantity must not exceed resting order quantity
>
> These invariants should be enforced at several levels.
>
> ## 6.2 Database constraints
>
> Use:
>
> - primary keys
> - foreign keys
> - unique constraints
> - check constraints
>
> Examples:
>
> - unique order identifier
> - quantity $> 0$
> - price $> 0$ for limit orders
> - status transitions constrained by allowed workflow
>
> ## 6.3 Single source of truth for money
>
> Never derive financial truth from caches or denormalized stores. The ledger database must be authoritative.
>
> For example, available cash should be computed as:
>
> $$
> \text{available cash} = \text{posted cash} - \text{reserved cash} - \text{margin hold}
> $$
>
> with all components stored in a consistent transactional model.
>
> ## 6.4 Deterministic matching
>
> The matching engine must apply deterministic rules:
>
> - price-time priority
> - tie-breaking by sequence number
> - strictly ordered processing per instrument
>
> Given the same event sequence, replay must produce the same book and trades.
>
> ## 6.5 Reconciliation
>
> Because distributed systems may still suffer integration errors, build reconciliation jobs that compare:
>
> - positions versus executions
> - balances versus ledger entries
> - internal state versus clearing broker state
> - event log versus materialized views
>
> Consistency is enforced not only at write time but also continuously by reconciliation.
>
> ---
>
> ## 7. Ensuring isolation
>
> Isolation prevents concurrent operations from observing or causing incorrect intermediate states.
>
> ## 7.1 Partition by instrument or account
>
> A common strategy is to process all orders for a given instrument in a single-threaded partition. Then the matching engine for that partition applies commands sequentially.
>
> This avoids race conditions such as two trades consuming the same resting quantity.
>
> Similarly, account-level reservation updates can be serialized by account shard.
>
> ## 7.2 Appropriate transaction isolation levels
>
> Different operations require different isolation guarantees.
>
> - `READ COMMITTED` may suffice for some reporting paths
> - `REPEATABLE READ` helps for stable reads within a transaction
> - `SERIALIZABLE` may be required for critical reservation logic if races are possible
>
> For example, if two simultaneous orders try to reserve the same funds, weaker isolation may cause oversubscription unless row locking or serialization is used.
>
> ## 7.3 Explicit locking
>
> Use row-level locking such as:
>
> $$
> \texttt{SELECT ... FOR UPDATE}
> $$
>
> when reserving account balances or modifying order state.
>
> This ensures two concurrent requests cannot both reserve the same available balance.
>
> ## 7.4 Optimistic concurrency control
>
> For high-throughput services, use version numbers:
>
> - read record with version $v$
> - update only if version is still $v$
> - otherwise retry
>
> This works well when conflicts are infrequent.
>
> ## 7.5 Separation of command and query paths
>
> A CQRS-style design helps:
>
> - command side enforces strong isolation
> - query side may use replicated, eventually consistent read models
>
> This preserves correctness without forcing every read path into expensive serializable transactions.
>
> ---
>
> ## 8. Ensuring durability
>
> Durability means committed transactions survive crashes.
>
> ## 8.1 Write-ahead logging
>
> Use storage engines with WAL. A transaction is acknowledged only after its log records are safely flushed according to the required durability policy.
>
> ## 8.2 Replication
>
> Maintain synchronous or semi-synchronous replication for critical data:
>
> - primary database
> - standby replicas
> - automated failover
>
> For the most critical ledger data, favor stronger durability even at some latency cost.
>
> ## 8.3 Append-only event log
>
> Persist all important domain events in an immutable event store or durable log such as Kafka plus database archival.
>
> Examples:
>
> - order received
> - order accepted
> - order rejected
> - trade executed
> - trade canceled
> - funds reserved
> - funds released
>
> This allows replay after failure and supports audit.
>
> ## 8.4 Snapshots and backup
>
> Keep:
>
> - frequent snapshots of order books
> - database backups
> - point-in-time recovery
> - offsite replicated archives
>
> Durability includes both crash recovery and disaster recovery.
>
> ---
>
> ## 9. Matching engine design
>
> The matching engine is usually the most latency-sensitive component.
>
> ## 9.1 Single-threaded per instrument shard
>
> For each instrument or partition:
>
> - one ordered input stream
> - one in-memory order book
> - one deterministic matching loop
>
> This design simplifies atomicity and isolation inside the engine.
>
> ## 9.2 Log first, then apply
>
> A robust pattern is:
>
> 1. assign sequence number
> 2. append command or event to durable log
> 3. apply to in-memory book
> 4. publish resulting events
>
> After restart, replay the log to rebuild the book.
>
> ## 9.3 Recovery
>
> On crash:
>
> - load latest snapshot
> - replay events after snapshot
> - restore exact order book state
>
> Because processing is deterministic, recovery is reliable.
>
> ---
>
> ## 10. Handling failures and partial outages
>
> A trading system must assume:
>
> - duplicate requests
> - service restarts
> - broker partition
> - network timeouts
> - downstream clearing failures
>
> ### Techniques
>
> - retries with idempotency
> - dead-letter queues for poison messages
> - circuit breakers for external dependencies
> - compensating actions for sagas
> - time-based expiration for stale reservations
> - watchdog reconciliation for “stuck” orders
>
> A crucial principle is that no financial state change should depend solely on transient in-memory state.
>
> ---
>
> ## 11. Example: atomic order placement
>
> Suppose a client places a buy order requiring $\text{\textdollar}10{,}000$ of reserved cash.
>
> ### Within one transaction
>
> 1. lock account row
> 2. verify available cash $\ge 10{,}000$
> 3. insert reservation record
> 4. insert order record with status `ACCEPTED`
> 5. insert outbox event `OrderAccepted`
> 6. commit
>
> If the system crashes after commit but before publishing the event, the outbox relay publishes it later. If the system crashes before commit, none of the changes persist.
>
> This satisfies atomicity.
>
> ---
>
> ## 12. Example: consistency during trade execution
>
> Suppose order $A$ buys $100$ shares and order $B$ sells $100$ shares.
>
> The execution transaction should ensure:
>
> - order $A$ remaining quantity decreases by $100$
> - order $B$ remaining quantity decreases by $100$
> - trade record for quantity $100$ is inserted
> - buyer position increases by $100$
> - seller position decreases by $100$
> - corresponding ledger entries balance
>
> The invariant
>
> $$
> \text{buyer increase} + \text{seller decrease} = 0
> $$
>
> must hold for asset quantity, and cash-side postings must also net correctly under double-entry accounting.
>
> ---
>
> ## 13. Technology choices
>
> A reasonable technology stack could be:
>
> - **API/OMS/Risk services**: Java, C++, or Go
> - **Matching engine**: C++ or Java for low latency
> - **Primary transactional store**: PostgreSQL or Oracle
> - **Event/log transport**: Kafka
> - **Cache/read models**: Redis, Elasticsearch
> - **Monitoring**: Prometheus, Grafana
> - **Tracing**: OpenTelemetry
>
> The exact choices matter less than the transactional discipline.
>
> ---
>
> ## 14. Practical trade-offs
>
> Strong ACID everywhere is often too expensive in a distributed low-latency platform. The typical approach is:
>
> - use strong ACID within bounded contexts such as ledger, reservations, and order state
> - use deterministic sequencing for matching
> - use event-driven propagation and reconciliation across services
> - use eventual consistency only for non-critical read models
>
> Thus, money-moving operations remain strongly correct, while scalability is preserved.
>
> ---
>
> ## 15. Summary
>
> To ensure atomicity, consistency, isolation, and durability in a trading system:
>
> ### Atomicity
> - local database transactions
> - outbox pattern
> - idempotency keys
> - sagas for distributed workflows
>
> ### Consistency
> - double-entry ledger
> - business invariant checks
> - database constraints
> - deterministic matching
> - reconciliation jobs
>
> ### Isolation
> - single-threaded processing per instrument shard
> - row locking or serializable reservation logic
> - optimistic concurrency where appropriate
> - separation of command and query paths
>
> ### Durability
> - write-ahead logging
> - replicated databases
> - immutable event logs
> - snapshots, backup, and replay
>
> ## Final design principle
>
> The most important architectural rule is:
>
> treat the **ledger and order state as authoritative transactional systems**, and treat all downstream views, analytics, and market-data projections as derived.
>
> This preserves financial correctness while still allowing a high-performance, scalable trading platform.
