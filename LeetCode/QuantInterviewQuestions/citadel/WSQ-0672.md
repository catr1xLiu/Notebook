> [!example] Question 672 · Citadel
> ## Software Engineer Interview

Implement a balanced binary search tree from scratch and explain its time complexity. Additionally, optimize the tree to efficiently handle duplicate values.

[Source](https://www.thewallstreetquants.com/ebook#p=673)

> [!success]- Solution (Click to expand)
> ## Balanced Binary Search Tree with Duplicate Optimization
>
> A suitable choice is an **AVL tree** or a **Red-Black tree**, since both maintain height balance and guarantee logarithmic-time operations. To optimize for duplicate values, store a **count** in each node rather than inserting equal keys as separate nodes.
>
> ---
>
> ## 1. Data Structure Design
>
> Each node stores:
>
> - the key
> - the number of occurrences of that key
> - pointers to left and right children
> - balancing metadata
>
> For an AVL tree, the node can be defined conceptually as:
>
> ```text
> Node:
>     key
>     count
>     height
>     left
>     right
> ```
>
> Here:
>
> - `key` is the stored value
> - `count` is the number of times the value appears
> - `height` is used to maintain AVL balance
>
> This modification is the main optimization for duplicates: if a value already exists, increment `count` instead of creating another node.
>
> ---
>
> ## 2. BST Property with Duplicates
>
> The binary search tree property becomes:
>
> - all keys in the left subtree are less than the node’s key
> - all keys in the right subtree are greater than the node’s key
> - if a key is equal to the node’s key, update `count`
>
> Thus, duplicate values do not increase tree height.
>
> ---
>
> ## 3. AVL Balancing Idea
>
> For each node, define the balance factor:
>
> $$
> \text{balance}(v) = \text{height}(v.\text{left}) - \text{height}(v.\text{right})
> $$
>
> An AVL tree requires:
>
> $$
> |\text{balance}(v)| \le 1
> $$
>
> After insertion or deletion, if this condition is violated, restore balance using rotations:
>
> - Left rotation
> - Right rotation
> - Left-right rotation
> - Right-left rotation
>
> ---
>
> ## 4. Insertion
>
> ### Case 1: Key is not present
> Insert as in a normal BST, then update heights and rebalance.
>
> ### Case 2: Key already exists
> Increment `count` and stop. No structural change is needed.
>
> ### Pseudocode
>
> ```text
> insert(node, key):
>     if node == null:
>         return new Node(key, count=1)
>
>     if key < node.key:
>         node.left = insert(node.left, key)
>     else if key > node.key:
>         node.right = insert(node.right, key)
>     else:
>         node.count += 1
>         return node
>
>     updateHeight(node)
>     return rebalance(node)
> ```
>
> ---
>
> ## 5. Deletion
>
> Deletion must handle duplicates carefully.
>
> ### Case 1: `count > 1`
> If the key is found and its count is greater than $1$, simply decrement:
>
> $$
> \text{count} \leftarrow \text{count} - 1
> $$
>
> No node removal is needed.
>
> ### Case 2: `count = 1`
> Perform normal BST deletion:
>
> - no child: remove node
> - one child: replace node with its child
> - two children: replace with inorder successor (or predecessor), then delete that replacement node
>
> After structural deletion, update heights and rebalance.
>
> ### Pseudocode
>
> ```text
> delete(node, key):
>     if node == null:
>         return null
>
>     if key < node.key:
>         node.left = delete(node.left, key)
>     else if key > node.key:
>         node.right = delete(node.right, key)
>     else:
>         if node.count > 1:
>             node.count -= 1
>             return node
>
>         if node.left == null:
>             return node.right
>         if node.right == null:
>             return node.left
>
>         successor = minNode(node.right)
>         node.key = successor.key
>         node.count = successor.count
>         successor.count = 1
>         node.right = delete(node.right, successor.key)
>
>     updateHeight(node)
>     return rebalance(node)
> ```
>
> The line `successor.count = 1` ensures that when the successor is deleted from the right subtree, the entire replacement node is removed correctly.
>
> ---
>
> ## 6. Search
>
> Search is identical to ordinary BST search:
>
> ```text
> search(node, key):
>     if node == null:
>         return false
>     if key < node.key:
>         return search(node.left, key)
>     if key > node.key:
>         return search(node.right, key)
>     return true
> ```
>
> If frequency is needed, return `node.count` instead of a boolean.
>
> ---
>
> ## 7. Rotations
>
> ### Right Rotation
>
> Used when the left subtree is too heavy.
>
> ```text
> rotateRight(y):
>     x = y.left
>     T2 = x.right
>
>     x.right = y
>     y.left = T2
>
>     updateHeight(y)
>     updateHeight(x)
>
>     return x
> ```
>
> ### Left Rotation
>
> Used when the right subtree is too heavy.
>
> ```text
> rotateLeft(x):
>     y = x.right
>     T2 = y.left
>
>     y.left = x
>     x.right = T2
>
>     updateHeight(x)
>     updateHeight(y)
>
>     return y
> ```
>
> ### Rebalancing Logic
>
> Let
>
> $$
> b = \text{balance}(node)
> $$
>
> Then:
>
> - if $b > 1$ and left child has nonnegative balance: right rotation
> - if $b > 1$ and left child has negative balance: left rotation on left child, then right rotation
> - if $b < -1$ and right child has nonpositive balance: left rotation
> - if $b < -1$ and right child has positive balance: right rotation on right child, then left rotation
>
> ---
>
> ## 8. Why Storing Counts Helps with Duplicates
>
> Without duplicate optimization, if many equal values are inserted, one must choose a rule such as “equal goes left” or “equal goes right.” This can create many extra nodes and may increase rebalancing work.
>
> With counts:
>
> - only one node is stored per distinct key
> - repeated insertions of the same value do not increase tree height
> - repeated deletions are cheaper when they only decrement `count`
> - memory usage improves from storing $k$ equal values in $k$ nodes to storing them in one node
>
> If there are $n$ total inserted values but only $m$ distinct values, the tree height depends on $m$, not $n$.
>
> Thus the height is:
>
> $$
> O(\log m)
> $$
>
> rather than depending on all occurrences individually.
>
> ---
>
> ## 9. Time Complexity
>
> Let $m$ be the number of **distinct** keys currently in the tree.
>
> ### Search
> A balanced BST has height:
>
> $$
> O(\log m)
> $$
>
> So search takes:
>
> $$
> O(\log m)
> $$
>
> ### Insertion
> - find the position: $O(\log m)$
> - possibly update `count`: $O(1)$
> - possibly rebalance using a constant number of rotations
>
> Therefore:
>
> $$
> O(\log m)
> $$
>
> ### Deletion
> - locate the key: $O(\log m)$
> - if `count > 1`, decrement in $O(1)$ after lookup
> - otherwise remove node and rebalance
>
> Therefore:
>
> $$
> O(\log m)
> $$
>
> ### Space
> One node per distinct key, so:
>
> $$
> O(m)
> $$
>
> If duplicates were stored separately, space would be:
>
> $$
> O(n)
> $$
>
> where $n$ is the total number of inserted values.
>
> ---
>
> ## 10. Summary of the Optimization
>
> To implement a balanced BST from scratch and optimize duplicate handling:
>
> 1. use a self-balancing BST such as an AVL tree
> 2. store a `count` field in each node
> 3. on duplicate insertion, increment `count`
> 4. on deletion, decrement `count` unless it becomes zero
> 5. rebalance only when the tree structure changes
>
> This gives:
>
> - **search:** $O(\log m)$
> - **insert:** $O(\log m)$
> - **delete:** $O(\log m)$
> - **space:** $O(m)$
>
> where $m$ is the number of distinct keys.
>
> ---
>
> ## Final Answer
>
> A correct and efficient implementation is an **AVL tree with a duplicate counter in each node**. Each node stores $(\text{key}, \text{count}, \text{height}, \text{left}, \text{right})$. Duplicate insertions increment `count` instead of creating new nodes, and deletions decrement `count` until it reaches $0$, at which point the node is removed normally. Because the tree remains balanced, search, insertion, and deletion each run in
>
> $$
> O(\log m)
> $$
>
> time, where $m$ is the number of distinct keys, and the space usage is
>
> $$
> O(m)
> $$
>
> This is more efficient than storing duplicates as separate nodes, especially when many repeated values occur.
