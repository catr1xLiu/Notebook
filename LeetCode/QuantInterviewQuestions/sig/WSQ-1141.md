> [!example] Question 1141 · SIG
> ## Software Engineer Interview

Since the average time complexity of a hashtable is O(1), why do we still use binary search trees? Can you describe some occasions where we use a binary search tree instead of a hashtable?

[Source](https://www.thewallstreetquants.com/ebook#p=1142)

> [!success]- Solution (Click to expand)
> A hash table and a binary search tree support different kinds of operations efficiently, so neither universally replaces the other.
>
> ## Main idea
>
> A hash table gives average-case $O(1)$ time for operations such as:
>
> - insert
> - search
> - delete
>
> However, this efficiency applies primarily to **exact-key lookup**. A binary search tree, especially a balanced one, gives $O(\log n)$ time for these operations while also preserving the **sorted order** of keys. That extra structure makes many operations possible or efficient that a hash table does not support well.
>
> ## Why a hash table is not always enough
>
> ### 1. No ordering of keys
>
> In a hash table, keys are distributed according to their hash values, not according to their natural order. Therefore, operations involving order are inefficient.
>
> For example, these are easy in a BST but hard in a hash table:
>
> - find the minimum or maximum key
> - find the predecessor or successor of a key
> - print all keys in sorted order
> - find all keys in a range such as $[a,b]$
>
> In a balanced BST:
>
> - $\min$ and $\max$ can be found in $O(\log n)$
> - predecessor/successor can be found in $O(\log n)$
> - range queries take $O(\log n + k)$, where $k$ is the number of reported elements
> - inorder traversal outputs all keys in sorted order in $O(n)$
>
> In a hash table, these typically require scanning all elements, which is $O(n)$.
>
> ---
>
> ### 2. Worst-case guarantees
>
> A hash table is usually said to have average-case $O(1)$ time, but in the worst case operations can degrade to $O(n)$ because of collisions.
>
> A balanced BST such as:
>
> - AVL tree
> - Red-Black tree
>
> provides guaranteed worst-case time:
>
> - search: $O(\log n)$
> - insert: $O(\log n)$
> - delete: $O(\log n)$
>
> So when predictable performance is important, BSTs are often preferred.
>
> ---
>
> ### 3. Ordered iteration
>
> If the data must be traversed in sorted order repeatedly, a BST is natural. An inorder traversal of a BST produces the keys in increasing order directly.
>
> A hash table does not maintain sorted order, so obtaining sorted output requires an additional sorting step of $O(n \log n)$.
>
> ---
>
> ### 4. Range queries
>
> Suppose one needs all elements with keys between $30$ and $80$.
>
> - In a BST, one can navigate to the relevant region and report only the needed nodes efficiently.
> - In a hash table, there is no structure relating nearby keys, so one usually checks every entry.
>
> Thus BSTs are much better for databases, indexes, interval-style queries, and similar tasks.
>
> ---
>
> ### 5. Closest-key queries
>
> Operations such as:
>
> - find the largest key $\le x$
> - find the smallest key $\ge x$
>
> are natural in BSTs and can be done in $O(\log n)$.
>
> A hash table offers no efficient support for such queries.
>
> ## Typical occasions where BST is used instead of a hash table
>
> A BST is preferred when the application needs any of the following:
>
> ### Ordered dictionaries or maps
> Examples:
> - maintaining a set of numbers in sorted order
> - implementing structures like `TreeMap` or `std::map`
>
> ### Range searching
> Examples:
> - all timestamps between $t_1$ and $t_2$
> - all scores between $50$ and $60$
>
> ### Predecessor/successor queries
> Examples:
> - next larger event time
> - previous version number
> - nearest scheduled appointment before a given time
>
> ### Frequent sorted traversal
> Examples:
> - printing records alphabetically
> - iterating through keys in increasing order
>
> ### Guaranteed logarithmic performance
> Examples:
> - systems where worst-case behavior matters more than average-case speed
>
> ## When a hash table is better
>
> A hash table is usually better when:
>
> - only exact lookup is needed
> - order does not matter
> - average-case speed is the main concern
>
> Examples:
> - checking whether a username exists
> - mapping an ID to a record
> - counting frequencies of words
>
> ## Conclusion
>
> Although hash tables have average-case $O(1)$ lookup, they do not maintain key order and do not support ordered operations efficiently. Binary search trees, especially balanced BSTs, are used when one needs:
>
> - sorted data
> - range queries
> - predecessor/successor operations
> - ordered traversal
> - stronger worst-case guarantees
>
> Thus, BSTs are chosen not because they beat hash tables on exact lookup, but because they support a richer set of order-based operations efficiently.
