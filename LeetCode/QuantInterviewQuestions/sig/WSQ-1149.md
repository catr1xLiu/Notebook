> ## Implementing a Garbage Collector
>
> A garbage collector automatically reclaims memory occupied by objects that are no longer reachable by a program. A practical implementation begins with a precise model of objects, roots, and reachability, and then chooses a collection strategy such as reference counting, mark-and-sweep, copying collection, or generational collection.
>
> ## 1. Memory model
>
> Assume the runtime allocates all heap objects in a managed heap. Each object typically contains:
>
> - a header, storing metadata such as size, type, and mark bits,
> - payload fields, some of which may be pointers to other objects.
>
> A simple object layout is:
>
> - header:
>   - size,
>   - type information,
>   - one mark bit,
> - fields:
>   - zero or more pointer or non-pointer values.
>
> The collector must know, for each object type, which fields are pointers. This is often done using type descriptors or pointer maps.
>
> ## 2. Reachability
>
> An object is considered **live** if it is reachable from a set of **roots**. Roots usually include:
>
> - global variables,
> - static variables,
> - registers,
> - stack variables of all active threads.
>
> Formally, if the heap is viewed as a directed graph and roots are distinguished entry points, then live objects are exactly those reachable from the roots by following pointer fields.
>
> The collector therefore needs two things:
>
> 1. a way to enumerate roots,
> 2. a way to traverse pointers inside objects.
>
> ## 3. A basic mark-and-sweep collector
>
> A standard first implementation is **mark-and-sweep**.
>
> ### 3.1 Allocation
>
> Maintain a list of heap blocks or use a bump-pointer allocator inside heap segments. When allocation fails because no free block is large enough, invoke garbage collection.
>
> ### 3.2 Mark phase
>
> Starting from the roots, recursively or iteratively visit all reachable objects and set their mark bit.
>
> Pseudocode:
>
> ```text
> mark(obj):
>     if obj == null or obj.marked:
>         return
>     obj.marked = true
>     for each pointer field p in obj:
>         mark(*p)
> ```
>
> To avoid recursion overflow, use an explicit stack:
>
> ```text
> mark_from_roots():
>     worklist = empty stack
>     for each root r:
>         if r points to object o and not o.marked:
>             push o onto worklist
>
>     while worklist not empty:
>         o = pop worklist
>         if o.marked:
>             continue
>         o.marked = true
>         for each pointer field p in o:
>             if p != null and not p.marked:
>                 push p
> ```
>
> ### 3.3 Sweep phase
>
> Scan all heap objects. If an object is marked, clear its mark bit for the next cycle and keep it. If it is unmarked, reclaim it and return its space to the free list.
>
> Pseudocode:
>
> ```text
> sweep():
>     for each object o in heap:
>         if o.marked:
>             o.marked = false
>         else:
>             free(o)
> ```
>
> ### 3.4 Correctness idea
>
> - Every reachable object is visited during marking because traversal starts from all roots and follows all pointers.
> - Every unreachable object remains unmarked and is reclaimed during sweeping.
> - Therefore only garbage is freed.
>
> ## 4. Required runtime support
>
> A collector cannot work without cooperation from the runtime system.
>
> ### 4.1 Root scanning
>
> The runtime must identify all roots:
>
> - globals are easy: scan a known range,
> - stacks require scanning each thread’s stack,
> - registers may need to be spilled to the stack at safe points.
>
> ### 4.2 Precise vs conservative collection
>
> A **precise** collector knows exactly which machine words are pointers.
>
> A **conservative** collector treats anything that looks like a pointer as a possible pointer. This is easier in low-level languages but may retain garbage accidentally.
>
> For a language implementation, a precise collector is preferable.
>
> ### 4.3 Safe points
>
> In a moving or stop-the-world collector, threads must pause only at positions where the runtime can find all live references. These are called **safe points**.
>
> ## 5. Copying collector
>
> Another common design is a **copying collector**, especially for young objects.
>
> ### 5.1 Idea
>
> Divide memory into two equal regions:
>
> - from-space,
> - to-space.
>
> Allocate objects sequentially in from-space using a bump pointer. When full, perform collection:
>
> 1. copy all reachable objects from from-space to to-space,
> 2. update references to their new addresses,
> 3. swap the roles of the two spaces.
>
> ### 5.2 Forwarding
>
> When an object is moved, leave a forwarding pointer in the old location so repeated visits can reuse the copied object.
>
> Pseudocode:
>
> ```text
> copy(o):
>     if o == null:
>         return null
>     if o has forwarding pointer:
>         return o.forwarded_to
>     new_o = allocate in to-space
>     copy contents of o into new_o
>     install forwarding pointer in o
>     for each pointer field p in new_o:
>         p = copy(p)
>     return new_o
> ```
>
> ### 5.3 Advantages and disadvantages
>
> Advantages:
>
> - allocation is extremely fast,
> - compacts memory automatically,
> - no fragmentation.
>
> Disadvantages:
>
> - requires extra memory,
> - moves objects, so all references must be updated,
> - harder to interface with unmanaged code.
>
> ## 6. Reference counting
>
> A simpler alternative is **reference counting**.
>
> Each object stores a count of how many references point to it.
>
> - On assignment of a pointer, increment the new target’s count.
> - Decrement the old target’s count.
> - When a count reaches $0$, reclaim the object and recursively decrement objects it referenced.
>
> ### Problem: cycles
>
> Reference counting cannot collect cyclic garbage. If two objects point to each other but are unreachable from the roots, both still have nonzero counts.
>
> For this reason, practical systems using reference counting often add a cycle detector.
>
> ## 7. Generational garbage collection
>
> Most modern collectors are **generational**, based on the empirical observation that most objects die young.
>
> ### 7.1 Heap organization
>
> Split the heap into:
>
> - a **young generation** for new objects,
> - an **old generation** for long-lived objects.
>
> Allocate new objects in the young generation. Collect it frequently using a copying collector. Promote surviving objects to the old generation after they survive enough collections.
>
> ### 7.2 Write barrier
>
> A young-generation collection must also find references from old objects into young objects. Scanning the whole old generation every time is too expensive.
>
> Use a **write barrier**: whenever a pointer field is updated, record old-to-young references in a remembered set.
>
> Example barrier:
>
> ```text
> store(obj.field, value):
>     obj.field = value
>     if obj is old and value is young:
>         add obj to remembered set
> ```
>
> During minor collection, scan:
>
> - roots,
> - remembered set.
>
> This yields high performance in practice.
>
> ## 8. Tri-color marking and incremental collection
>
> To reduce pause times, use **incremental** or **concurrent** collection. A standard abstraction is tri-color marking:
>
> - **white**: not yet discovered,
> - **gray**: discovered but children not fully scanned,
> - **black**: discovered and fully scanned.
>
> The invariant is typically that no black object points to a white object. If a mutator writes such a pointer during marking, a write barrier must preserve the invariant.
>
> Two common barrier styles are:
>
> - **Dijkstra barrier**: shade the new target,
> - **Yuasa barrier**: shade the overwritten reference source or preserve the old target.
>
> These techniques allow garbage collection to proceed alongside program execution.
>
> ## 9. Finalization and weak references
>
> A complete collector must also handle special object behaviors.
>
> ### 9.1 Finalizers
>
> Objects with finalizers require care:
>
> - they cannot be reclaimed immediately when first found unreachable,
> - finalization order is subtle,
> - resurrection is possible if a finalizer stores the object somewhere reachable.
>
> Because of these complexities, finalizers should be minimized.
>
> ### 9.2 Weak references
>
> Weak references do not keep objects alive. During collection:
>
> 1. determine ordinary reachability,
> 2. clear weak references to unreachable objects,
> 3. optionally enqueue notifications.
>
> Weak maps, weak sets, and caches rely on this behavior.
>
> ## 10. A practical implementation plan
>
> A reasonable implementation strategy for a new language runtime is:
>
> ### Step 1: precise stop-the-world mark-and-sweep
>
> Implement:
>
> - object headers with mark bits,
> - type descriptors describing pointer fields,
> - root enumeration for globals, stacks, and registers,
> - stop-the-world collection at allocation failure.
>
> This is easy to reason about and debug.
>
> ### Step 2: improve allocation
>
> Use:
>
> - size classes for small objects,
> - free lists or segregated lists,
> - large-object space for big allocations.
>
> ### Step 3: add compaction or copying nursery
>
> To reduce fragmentation and improve allocation speed, add:
>
> - a copying young generation,
> - mark-sweep or mark-compact old generation.
>
> ### Step 4: add barriers and remembered sets
>
> This enables generational collection.
>
> ### Step 5: reduce pauses
>
> Introduce:
>
> - incremental marking,
> - concurrent marking,
> - parallel sweeping.
>
> ## 11. Example architecture
>
> A robust collector for a modern language might be:
>
> - **young generation**: copying collector using bump-pointer allocation,
> - **old generation**: mark-sweep or mark-compact,
> - **minor GC**: collect young generation only,
> - **major GC**: collect whole heap,
> - **write barrier**: track old-to-young pointers,
> - **precise stack maps**: identify roots exactly at safe points.
>
> This design balances:
>
> - fast allocation,
> - good throughput,
> - acceptable pause times,
> - manageable implementation complexity.
>
> ## 12. Key engineering issues
>
> Several practical issues dominate real implementations:
>
> - **pointer identification**: exact metadata is essential,
> - **fragmentation**: mark-sweep may fragment memory,
> - **pause times**: stop-the-world collectors can stall programs,
> - **threading**: all mutator threads must synchronize with the collector,
> - **foreign code**: native interfaces complicate root tracking and moving objects,
> - **pinning**: some objects must remain unmoved for interoperability,
> - **testing**: collectors require stress testing with adversarial object graphs.
>
> ## 13. Minimal mark-and-sweep algorithm summary
>
> A minimal collector can be implemented as follows:
>
> 1. Store all heap objects in managed regions.
> 2. Attach metadata to each object:
>    - size,
>    - type,
>    - mark bit.
> 3. At collection time:
>    - pause all threads,
>    - enumerate roots,
>    - mark all reachable objects,
>    - sweep unmarked objects into free lists,
>    - resume execution.
> 4. Trigger collection when allocated memory exceeds a threshold.
>
> Its asymptotic cost per full collection is approximately linear in the heap size, namely $O(H)$, where $H$ is the number of heap objects or total heap memory scanned.
>
> ## Final answer
>
> A garbage collector is implemented by defining heap objects and roots, computing reachability from the roots, and reclaiming unreachable objects. The simplest correct implementation is a **precise stop-the-world mark-and-sweep collector**:
>
> 1. represent every heap object with a header containing at least a mark bit and type descriptor,
> 2. maintain metadata describing which fields are pointers,
> 3. pause execution at collection time,
> 4. enumerate all roots from globals, stacks, and registers,
> 5. mark all objects reachable from those roots,
> 6. sweep the heap and free every unmarked object.
>
> A practical modern collector usually evolves into a **generational design** with:
>
> - a **copying young generation** for fast allocation and short-lived objects,
> - a **mark-sweep or mark-compact old generation** for long-lived objects,
> - **write barriers** and **remembered sets** to track cross-generation pointers.
>
> This combination gives good performance while preserving correctness.
