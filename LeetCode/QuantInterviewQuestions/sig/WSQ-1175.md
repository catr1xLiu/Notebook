> ## 1. Data processing with reading from a file
>
> A standard approach in C++ is:
>
> 1. Open the file with an input stream.
> 2. Check whether the file opened successfully.
> 3. Read data in a loop.
> 4. Process each record.
> 5. Close the file automatically when the stream goes out of scope.
>
> ### Example: reading integers and computing their sum
>
> ```cpp
> #include <iostream>
> #include <fstream>
> #include <vector>
>
> int main() {
>     std::ifstream file("data.txt");
>     if (!file) {
>         std::cerr << "Failed to open file\n";
>         return 1;
>     }
>
>     std::vector<int> values;
>     int x;
>     while (file >> x) {
>         values.push_back(x);
>     }
>
>     long long sum = 0;
>     for (int v : values) {
>         sum += v;
>     }
>
>     std::cout << "Count: " << values.size() << "\n";
>     std::cout << "Sum: " << sum << "\n";
>     return 0;
> }
> ```
>
> ### Line-by-line processing
>
> If the file is text-based and each line must be parsed separately, use `std::getline`.
>
> ```cpp
> #include <iostream>
> #include <fstream>
> #include <string>
>
> int main() {
>     std::ifstream file("input.txt");
>     if (!file) {
>         std::cerr << "Cannot open file\n";
>         return 1;
>     }
>
>     std::string line;
>     while (std::getline(file, line)) {
>         std::cout << "Read line: " << line << "\n";
>     }
> }
> ```
>
> ### Common issues
>
> - Reading with `while (!file.eof())` is incorrect. Prefer `while (file >> x)` or `while (std::getline(file, line))`.
> - Always check that the file opened successfully.
> - If mixing formatted input and line input, be careful about leftover newline characters.

> ## 2. What is `std::vector`? Difference between `vector` and array; memory management
>
> ### What is a `std::vector`?
>
> `std::vector<T>` is a dynamic array provided by the C++ Standard Library. It stores elements contiguously in memory and can grow or shrink at runtime.
>
> Example:
>
> ```cpp
> #include <vector>
>
> std::vector<int> v;
> v.push_back(10);
> v.push_back(20);
> ```
>
> The vector manages its own memory automatically.
>
> ### Array vs `std::vector`
>
> #### Built-in array
>
> ```cpp
> int arr[5] = {1, 2, 3, 4, 5};
> ```
>
> Properties:
>
> - Fixed size.
> - Size must be known at creation.
> - Does not manage resizing.
> - In many contexts decays to a pointer.
> - Usually stack-allocated if local.
>
> #### `std::vector`
>
> ```cpp
> std::vector<int> v = {1, 2, 3, 4, 5};
> ```
>
> Properties:
>
> - Dynamic size.
> - Can grow with `push_back`.
> - Stores elements contiguously.
> - Knows its own size via `v.size()`.
> - Handles allocation and deallocation automatically.
> - Typically uses heap memory for storage.
>
> ### Key differences
>
> - **Feature Size** — Array: Fixed; `std::vector`: Dynamic
> - **Feature Memory management** — Array: Manual or automatic depending on context; `std::vector`: Automatic
> - **Feature Can resize** — Array: No; `std::vector`: Yes
> - **Feature Knows size** — Array: Not intrinsically; `std::vector`: Yes
> - **Feature Copy semantics** — Array: Limited and tricky for raw arrays; `std::vector`: Safe value semantics
> - **Feature Standard library support** — Array: Limited; `std::vector`: Rich interface
>
> ### Memory management of `std::vector`
>
> A vector typically maintains:
>
> - a pointer to allocated storage,
> - the current number of elements,
> - the current capacity.
>
> When capacity is exceeded, the vector:
>
> 1. Allocates a larger memory block,
> 2. Moves or copies elements,
> 3. Destroys old elements,
> 4. Frees old storage.
>
> Example:
>
> ```cpp
> std::vector<int> v;
> v.push_back(1);
> v.push_back(2);
> v.push_back(3);
> ```
>
> As elements are added, reallocation may occur. This can invalidate pointers, references, and iterators to elements.
>
> ### Capacity vs size
>
> - `v.size()` = number of actual elements.
> - `v.capacity()` = amount of allocated storage.
>
> ```cpp
> std::vector<int> v;
> v.reserve(100); // preallocate space
> ```
>
> Using `reserve` can improve performance when the approximate size is known in advance.
>
> ### When to use which
>
> - Use arrays for fixed-size data known at compile time.
> - Use `std::vector` for almost all dynamic sequence storage tasks.

> ## 3. Thread implementation debugging
>
> Debugging thread code usually involves checking for:
>
> 1. Data races,
> 2. Deadlocks,
> 3. Lifetime issues,
> 4. Incorrect synchronization,
> 5. Forgotten `join()` or `detach()`.
>
> ### Example of a race condition
>
> ```cpp
> #include <iostream>
> #include <thread>
>
> int counter = 0;
>
> void work() {
>     for (int i = 0; i < 100000; ++i) {
>         ++counter;
>     }
> }
>
> int main() {
>     std::thread t1(work);
>     std::thread t2(work);
>
>     t1.join();
>     t2.join();
>
>     std::cout << counter << "\n";
> }
> ```
>
> This is incorrect because both threads modify `counter` without synchronization. The result is undefined behavior.
>
> ### Fix with a mutex
>
> ```cpp
> #include <iostream>
> #include <thread>
> #include <mutex>
>
> int counter = 0;
> std::mutex m;
>
> void work() {
>     for (int i = 0; i < 100000; ++i) {
>         std::lock_guard<std::mutex> lock(m);
>         ++counter;
>     }
> }
>
> int main() {
>     std::thread t1(work);
>     std::thread t2(work);
>
>     t1.join();
>     t2.join();
>
>     std::cout << counter << "\n";
> }
> ```
>
> ### Better fix with `std::atomic`
>
> For a simple counter, atomic operations are more appropriate.
>
> ```cpp
> #include <iostream>
> #include <thread>
> #include <atomic>
>
> std::atomic<int> counter{0};
>
> void work() {
>     for (int i = 0; i < 100000; ++i) {
>         ++counter;
>     }
> }
>
> int main() {
>     std::thread t1(work);
>     std::thread t2(work);
>
>     t1.join();
>     t2.join();
>
>     std::cout << counter << "\n";
> }
> ```
>
> ### Common debugging checklist
>
> #### 1. Ensure every thread is joined or detached
>
> If a `std::thread` object is destroyed while still joinable, the program terminates.
>
> ```cpp
> std::thread t(work);
> t.join();
> ```
>
> #### 2. Protect shared data
>
> If multiple threads access the same object and at least one thread writes, synchronization is required.
>
> #### 3. Avoid deadlock
>
> Bad example:
>
> ```cpp
> std::mutex m1, m2;
> ```
>
> If one thread locks `m1` then `m2`, while another locks `m2` then `m1`, a deadlock may occur.
>
> Use consistent lock ordering or `std::scoped_lock`.
>
> ```cpp
> std::scoped_lock lock(m1, m2);
> ```
>
> #### 4. Watch object lifetimes
>
> A thread must not access objects that have already been destroyed.
>
> Bad pattern:
>
> ```cpp
> void start_thread() {
>     int x = 42;
>     std::thread t([&]() {
>         std::cout << x << "\n";
>     });
>     t.detach();
> }
> ```
>
> Here the detached thread may use `x` after `x` has gone out of scope.
>
> #### 5. Use tools
>
> Useful tools include:
>
> - Thread sanitizers,
> - Address sanitizers,
> - Debuggers,
> - Logging with thread identifiers.
>
> Example compilation with sanitizer:
>
> ```bash
> g++ -std=c++17 -fsanitize=thread -g file.cpp
> ```

> ## 4. Implementing `std::shared_ptr` from scratch
>
> A simplified `shared_ptr` requires:
>
> 1. A raw pointer to the managed object,
> 2. A reference count stored in shared control data,
> 3. Copy semantics that increase the count,
> 4. Destruction semantics that decrease the count,
> 5. Deletion when the count reaches $0$.
>
> ### Simplified implementation
>
> ```cpp
> #include <cstddef>
> #include <utility>
>
> template <typename T>
> class SharedPtr {
> private:
>     T* ptr;
>     std::size_t* count;
>
>     void release() {
>         if (count) {
>             --(*count);
>             if (*count == 0) {
>                 delete ptr;
>                 delete count;
>             }
>         }
>     }
>
> public:
>     SharedPtr() : ptr(nullptr), count(nullptr) {}
>
>     explicit SharedPtr(T* p) : ptr(p), count(nullptr) {
>         if (p) {
>             count = new std::size_t(1);
>         }
>     }
>
>     SharedPtr(const SharedPtr& other) : ptr(other.ptr), count(other.count) {
>         if (count) {
>             ++(*count);
>         }
>     }
>
>     SharedPtr& operator=(const SharedPtr& other) {
>         if (this != &other) {
>             release();
>             ptr = other.ptr;
>             count = other.count;
>             if (count) {
>                 ++(*count);
>             }
>         }
>         return *this;
>     }
>
>     SharedPtr(SharedPtr&& other) noexcept : ptr(other.ptr), count(other.count) {
>         other.ptr = nullptr;
>         other.count = nullptr;
>     }
>
>     SharedPtr& operator=(SharedPtr&& other) noexcept {
>         if (this != &other) {
>             release();
>             ptr = other.ptr;
>             count = other.count;
>             other.ptr = nullptr;
>             other.count = nullptr;
>         }
>         return *this;
>     }
>
>     ~SharedPtr() {
>         release();
>     }
>
>     T& operator*() const {
>         return *ptr;
>     }
>
>     T* operator->() const {
>         return ptr;
>     }
>
>     T* get() const {
>         return ptr;
>     }
>
>     std::size_t use_count() const {
>         return count ? *count : 0;
>     }
>
>     explicit operator bool() const {
>         return ptr != nullptr;
>     }
> };
> ```
>
> ### How it works
>
> Suppose:
>
> ```cpp
> SharedPtr<int> p1(new int(5));
> SharedPtr<int> p2 = p1;
> ```
>
> Then:
>
> - `p1.ptr` and `p2.ptr` point to the same integer.
> - `p1.count` and `p2.count` point to the same reference counter.
> - The counter becomes $2$.
>
> When one object is destroyed, the count becomes $1$.
> When the last owner is destroyed, the integer and the counter are both deleted.
>
> ### Important limitations of this simplified version
>
> This is not a full replacement for `std::shared_ptr`. Missing features include:
>
> - Thread-safe reference counting,
> - Custom deleters,
> - Weak references via `std::weak_ptr`,
> - Aliasing constructor,
> - Support for arrays,
> - Exception-safe control block design,
> - `make_shared` optimization.
>
> ### Thread-safe refinement
>
> Real `std::shared_ptr` uses atomic reference counting, because multiple threads may copy and destroy shared pointers concurrently.
>
> A rough improvement would be:
>
> ```cpp
> #include <atomic>
> ```
>
> and then use:
>
> ```cpp
> std::atomic<std::size_t>* count;
> ```
>
> However, a production-quality implementation requires a proper control block design.
>
> ### Core idea
>
> The essence of shared ownership is:
>
> - many pointer objects may own the same resource,
> - ownership is tracked by a shared counter,
> - the resource is destroyed exactly once, when the owner count becomes $0$.
>
> ## Final summary
>
> - File processing in C++ is commonly done with `std::ifstream`, checking open success and reading with stream-based loops.
> - `std::vector` is a dynamic contiguous container with automatic memory management, unlike fixed-size arrays.
> - Thread debugging focuses on races, deadlocks, synchronization correctness, object lifetime, and proper thread joining.
> - A simplified `shared_ptr` can be implemented using a managed pointer and a shared reference count, with copy/move/destructor logic to enforce shared ownership.
