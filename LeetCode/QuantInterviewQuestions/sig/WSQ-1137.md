> # Hash Tables
>
> A **hash table** is a data structure that stores **key–value pairs** and supports, on average, very fast operations:
>
> - **insert** a pair $(k, v)$,
> - **search** for the value associated with key $k$,
> - **delete** the key $k$.
>
> Its average running time for these operations is typically $O(1)$.
>
> ## 1. Basic idea
>
> A hash table uses an **array** of fixed size $m$ called **buckets** or **slots**. Since keys may be strings, numbers, or other objects, the table uses a **hash function** to convert a key into an array index.
>
> A hash function has the form
>
> $$
> h(k) \in \{0,1,\dots,m-1\}.
> $$
>
> Thus, instead of searching through all stored keys, the table computes $h(k)$ and goes directly to the corresponding slot.
>
> ### Example
>
> Suppose the table has size $m = 10$, and the hash function is
>
> $$
> h(k) = k \bmod 10.
> $$
>
> Then:
>
> - key $42$ goes to slot $2$,
> - key $17$ goes to slot $7$,
> - key $35$ goes to slot $5$.
>
> This is the source of the speed: the key is transformed directly into a location.
>
> ## 2. The problem of collisions
>
> Different keys can produce the same hash value. This is called a **collision**.
>
> For example, with
>
> $$
> h(k) = k \bmod 10,
> $$
>
> both $12$ and $22$ map to slot $2$.
>
> Since collisions are unavoidable in practice, hash tables must include a **collision-resolution strategy**.
>
> ## 3. Collision resolution methods
>
> There are two main methods.
>
> ### 3.1 Chaining
>
> In **chaining**, each array slot stores a small collection, often a linked list, of all key–value pairs whose keys hash to that slot.
>
> If keys $12$, $22$, and $32$ all hash to slot $2$, then bucket $2$ contains a chain like
>
> $$
> (12, v_1) \to (22, v_2) \to (32, v_3).
> $$
>
> #### Operations with chaining
>
> - **Search**: compute $h(k)$, go to that bucket, and scan the chain for key $k$.
> - **Insert**: compute $h(k)$ and add the new pair to the chain.
> - **Delete**: compute $h(k)$, find the key in the chain, and remove it.
>
> If the hash function distributes keys evenly, the chains stay short, so the average cost remains small.
>
> ### 3.2 Open addressing
>
> In **open addressing**, all key–value pairs are stored directly in the array. If a collision occurs, the table probes other slots according to a rule until an empty slot or the target key is found.
>
> Common probing rules include:
>
> - **Linear probing**:
>   $$
>   h(k),\ h(k)+1,\ h(k)+2,\dots \pmod m
>   $$
> - **Quadratic probing**
> - **Double hashing**
>
> #### Example: linear probing
>
> Suppose $m = 10$ and
>
> $$
> h(k) = k \bmod 10.
> $$
>
> Insert:
>
> - $12 \to 2$,
> - $22 \to 2$ but slot $2$ is occupied, so try $3$,
> - $32 \to 2$, then $3$, then $4$.
>
> The array might contain:
>
> - slot $2$: key $12$,
> - slot $3$: key $22$,
> - slot $4$: key $32$.
>
> #### Operations with open addressing
>
> - **Search**: follow the same probe sequence until the key is found or an empty slot is encountered.
> - **Insert**: probe until an empty slot is found.
> - **Delete**: more delicate; often a special marker such as “deleted” is used so searches are not broken.
>
> ## 4. Why hash tables are fast
>
> The efficiency depends on how full the table is. This is measured by the **load factor**.
>
> - For chaining,
>   $$
>   \alpha = \frac{n}{m},
>   $$
>   where $n$ is the number of stored keys and $m$ is the number of buckets.
>
> A small load factor means few keys per bucket on average.
>
> - For open addressing, $\alpha = n/m$ must stay below $1$, and performance worsens significantly as $\alpha$ approaches $1$.
>
> Under good hashing and controlled load factor:
>
> - average **search** time is $O(1)$,
> - average **insert** time is $O(1)$,
> - average **delete** time is $O(1)$.
>
> However, in the **worst case**, many keys may collide, and an operation can take $O(n)$.
>
> ## 5. What makes a good hash function
>
> A good hash function should:
>
> 1. be **fast** to compute,
> 2. distribute keys **uniformly** across the table,
> 3. minimize patterns that cause many collisions.
>
> For strings, a hash function often combines character codes in a way that spreads similar strings to different buckets.
>
> For example, the strings `"abc"` and `"acb"` should ideally produce very different hash values.
>
> ## 6. Resizing and rehashing
>
> As more elements are inserted, the load factor increases and performance degrades. To maintain efficiency, the table is often **resized**.
>
> Typical strategy:
>
> 1. allocate a larger array, often about twice the old size,
> 2. recompute the hash position of every existing key,
> 3. insert all items into the new table.
>
> This process is called **rehashing**.
>
> Although one resize is expensive, it happens only occasionally, so the **amortized** cost of insertion remains $O(1)$.
>
> ## 7. Example workflow
>
> Suppose a hash table of size $5$ uses chaining and
>
> $$
> h(k) = k \bmod 5.
> $$
>
> Insert keys $7$, $12$, $14$, $9$:
>
> - $7 \mapsto 2$,
> - $12 \mapsto 2$,
> - $14 \mapsto 4$,
> - $9 \mapsto 4$.
>
> The table becomes:
>
> - bucket $0$: empty,
> - bucket $1$: empty,
> - bucket $2$: $7 \to 12$,
> - bucket $3$: empty,
> - bucket $4$: $14 \to 9$.
>
> To search for $12$:
>
> 1. compute
>    $$
>    h(12) = 2,
>    $$
> 2. examine bucket $2$,
> 3. scan the chain until key $12$ is found.
>
> ## 8. Advantages and disadvantages
>
> ### Advantages
>
> - Very fast average-case lookup, insertion, and deletion.
> - Simple interface based on keys.
> - Widely used in dictionaries, symbol tables, caches, and database indexing.
>
> ### Disadvantages
>
> - Performance depends heavily on the hash function.
> - Collisions are unavoidable.
> - No natural ordering of keys.
> - Worst-case time can be $O(n)$.
> - Resizing can be expensive when it occurs.
>
> ## 9. Common uses
>
> Hash tables are used in:
>
> - dictionaries/maps,
> - sets,
> - compiler symbol tables,
> - caches,
> - memoization,
> - database hash indexes.
>
> ## Conclusion
>
> A hash table stores key–value pairs in an array and uses a hash function
>
> $$
> h(k)
> $$
>
> to map each key to a bucket. Because different keys may map to the same bucket, collisions must be handled, usually by **chaining** or **open addressing**. With a good hash function and a controlled load factor, the main operations run in average time
>
> $$
> O(1).
> $$
>
> This makes hash tables one of the most important and practical data structures in computing.
