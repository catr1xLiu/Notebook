> [!example] Question 1249 · SIG
> ## Technology Associate Interview

When using a virtual method, how does the machine determine to call the derived class's implementation rather than the base class implementation, under the hood?

[Source](https://www.thewallstreetquants.com/ebook#p=1250)

> [!success]- Solution (Click to expand)
> In most object-oriented languages that support virtual methods, the dispatch is implemented with a **virtual method table** (usually called a **vtable**) together with a hidden pointer inside each object.
>
> ## Basic idea
>
> If a base class declares a method as virtual, then a call such as
>
> $$
> p \to f()
> $$
>
> cannot be resolved solely from the static type of $p$. The actual object might be of a derived type, so the program must determine at runtime which implementation of $f$ to invoke.
>
> To make this efficient, each object typically carries a hidden pointer, often called the **vptr**, that points to the vtable for its actual runtime type.
>
> ## Structure under the hood
>
> Suppose there is a class hierarchy:
>
> - base class $B$
> - derived class $D$
>
> and both have a virtual method $f$, with $D$ overriding $B::f$.
>
> ### 1. Each class has a vtable
>
> Conceptually, the compiler creates tables like:
>
> - vtable for $B$: contains address of $B::f$
> - vtable for $D$: contains address of $D::f$
>
> So the table entries might look like:
>
> $$
> \text{vtable}_B[f] = \&B::f
> $$
>
> $$
> \text{vtable}_D[f] = \&D::f
> $$
>
> If there are several virtual functions, the table has one slot per virtual function.
>
> ### 2. Each object stores a pointer to its class's vtable
>
> A $B$ object contains a hidden field:
>
> $$
> \text{obj.vptr} = \text{vtable}_B
> $$
>
> A $D$ object contains:
>
> $$
> \text{obj.vptr} = \text{vtable}_D
> $$
>
> Thus, although a pointer may be typed as $B^*$, the actual object in memory still knows that it is a $D$ object because its hidden vptr points to $\text{vtable}_D$.
>
> ## What happens during a virtual call
>
> Consider:
>
> ```cpp
> B* p = new D;
> p->f();
> ```
>
> The generated code is conceptually like this:
>
> 1. Read the hidden vptr from the object pointed to by $p$.
> 2. Use that vptr to find the function pointer for slot $f$ in the vtable.
> 3. Call that function.
>
> In pseudocode:
>
> $$
> \text{func} = p \to \text{vptr}[f]
> $$
>
> $$
> \text{call func}(p)
> $$
>
> Since $p$ actually points to a $D$ object, its vptr points to $\text{vtable}_D$, so the lookup yields:
>
> $$
> \text{func} = \&D::f
> $$
>
> and therefore $D::f$ is called.
>
> ## Why the base pointer still works
>
> Even if the variable has static type $B^*$, the object itself is laid out so that the base-class part appears in a predictable location, and the hidden vptr reflects the true dynamic type. Thus the machine does not rely on the pointer's declared type alone; it follows the vptr stored in the object.
>
> ## Non-virtual call contrast
>
> If the method is not virtual, then the compiler binds the call using the static type at compile time. For
>
> ```cpp
> B* p = new D;
> p->g();
> ```
>
> where $g$ is non-virtual, the compiler emits a direct call to $B::g$:
>
> $$
> \text{call } B::g
> $$
>
> No vtable lookup is performed.
>
> ## Constructor and destructor detail
>
> During construction and destruction, the vptr may be temporarily set to the vtable of the class whose constructor or destructor is currently executing. This is why virtual dispatch inside constructors and destructors often behaves differently from ordinary runtime dispatch.
>
> ## Cost
>
> A virtual call usually adds:
>
> - one hidden pointer in the object,
> - one table per class with virtual methods,
> - one extra indirection at call time.
>
> This is typically much cheaper than searching by name or type dynamically.
>
> ## Conclusion
>
> The machine calls the derived implementation because the actual object carries hidden runtime type information in the form of a vptr. A virtual call is compiled as a lookup through the object's vtable, and the vtable for the derived class contains the address of the derived override. Thus a call through a base-class pointer can still invoke the correct derived-class method.
