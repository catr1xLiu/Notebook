> ## Software Engineer Interview

How would you implement a garbage collector for a programming language?

> ## Implementing a Garbage Collector
>
> A garbage collector automatically reclaims memory occupied by objects that are no longer reachable by a running program. A practical implementation begins by defining the runtime memory model, then choosing a collection strategy, and finally integrating allocation, object tracing, and reclamation.
>
> ---
>
> ## 1. Memory Model
>
> Assume the language runtime stores heap-allocated objects in managed memory. Each object typically contains:
>
> - A header
> - Type information
> - Size information
> - Possibly a mark bit, forwarding pointer, or generation metadata
> - The object payload, which may include pointers to other objects
>
> A simple object layout is:
>
> $$
> \text{Object} = \text{Header} \;\|\; \text{Fields}
> $$
>
> The collector must know, for each object, which fields are pointers and which are plain data. This may be provided by:
>
> - runtime type descriptors,
> - compiler-generated stack maps,
> - tagged pointers,
> - conservative scanning rules.
>
> ---
>
> ## 2. Fundamental Idea: Reachability
>
> An object is considered live if it is reachable from a set of root references. Typical roots are:
>
> - global variables,
> - static fields,
> - registers,
> - local variables on thread stacks,
> - active closures or continuations.
>
> Let $R$ be the set of roots and let the heap objects form a directed graph where edges are pointer references. An object $x$ is live if there exists a path from some $r \in R$ to $x$.
>
> The garbage collector’s task is therefore:
>
> 1. find all reachable objects,
> 2. reclaim all unreachable ones.
>
> ---
>
> ## 3. A Simple First Design: Mark-and-Sweep
>
> The most straightforward collector is **mark-and-sweep**.
>
> ### 3.1 Allocation
>
> Maintain a heap area and a free list of unused blocks. When the program requests a new object:
>
> 1. search the free list for a block of sufficient size,
> 2. split the block if necessary,
> 3. initialize the object header,
> 4. return the object pointer.
>
> If no block is large enough, run garbage collection.
>
> ---
>
> ### 3.2 Mark Phase
>
> The mark phase traverses all objects reachable from the roots.
>
> Each object has a mark bit initially set to $0$. During marking:
>
> 1. initialize a worklist with all root pointers,
> 2. repeatedly pop an object from the worklist,
> 3. if it is unmarked:
>    - mark it,
>    - scan its pointer fields,
>    - push referenced objects onto the worklist.
>
> Pseudo-code:
>
> ```text
> mark(roots):
>     worklist = roots
>     while worklist not empty:
>         obj = worklist.pop()
>         if obj == null: continue
>         if obj.marked: continue
>         obj.marked = true
>         for each pointer field p in obj:
>             worklist.push(p)
> ```
>
> This computes the reachable set.
>
> ---
>
> ### 3.3 Sweep Phase
>
> After marking, linearly scan the heap:
>
> - if an object is marked, clear its mark bit for the next cycle;
> - if it is unmarked, it is garbage and its memory is returned to the free list.
>
> Pseudo-code:
>
> ```text
> sweep(heap):
>     for each object obj in heap:
>         if obj.marked:
>             obj.marked = false
>         else:
>             free(obj)
> ```
>
> ---
>
> ### 3.4 Properties
>
> Advantages:
>
> - conceptually simple,
> - handles cyclic data naturally,
> - works for variable-sized objects.
>
> Disadvantages:
>
> - requires stopping the program during collection,
> - sweeping the entire heap can be slow,
> - causes memory fragmentation.
>
> ---
>
> ## 4. Improving Allocation: Mark-and-Compact
>
> To reduce fragmentation, a collector may move live objects together and leave one contiguous free region.
>
> ### 4.1 Outline
>
> A compacting collector typically performs:
>
> 1. **mark** all reachable objects,
> 2. **compute new locations** for live objects,
> 3. **update pointers** to those new locations,
> 4. **move objects**.
>
> If object $o$ moves from address $a$ to address $a'$, all pointers that previously referenced $a$ must be updated to $a'$.
>
> This requires either:
>
> - a forwarding pointer in the old object header, or
> - a separate relocation table.
>
> ### 4.2 Benefit
>
> Compaction enables fast allocation using a bump pointer:
>
> $$
> \text{alloc}(n): \quad p = \text{heap\_top}, \quad \text{heap\_top} \mathrel{+}= n
> $$
>
> This is much faster than free-list allocation.
>
> ---
>
> ## 5. Copying Collection
>
> A particularly elegant moving collector is the **copying collector**, often implemented with two semispaces.
>
> ### 5.1 Heap Organization
>
> Split the heap into two equal regions:
>
> - **from-space**
> - **to-space**
>
> Allocation occurs linearly in from-space. When full:
>
> 1. start with an empty to-space,
> 2. copy all reachable objects from from-space into to-space,
> 3. update all references,
> 4. swap the two spaces.
>
> Unreachable objects are simply left behind.
>
> ### 5.2 Cheney’s Algorithm
>
> A standard breadth-first copying collector proceeds as follows:
>
> 1. copy root objects into to-space,
> 2. maintain two pointers:
>    - $scan$: next copied object whose fields must be scanned,
>    - $free$: next free location in to-space,
> 3. while $scan < free$:
>    - inspect the object at $scan$,
>    - for each pointer field:
>      - if the referenced object has not been copied, copy it to $free$ and install a forwarding pointer,
>      - replace the field with the new address,
>    - advance $scan$.
>
> Pseudo-code:
>
> ```text
> collect():
>     swap(from_space, to_space)
>     free = to_space.start
>     for each root r:
>         r = copy(r)
>     scan = to_space.start
>     while scan < free:
>         obj = scan
>         for each pointer field p in obj:
>             p = copy(p)
>         scan += size(obj)
>
> copy(obj):
>     if obj == null: return null
>     if obj in to_space: return obj
>     if obj has forwarding pointer:
>         return obj.forward
>     new_obj = free
>     free += size(obj)
>     memcpy(new_obj, obj)
>     obj.forward = new_obj
>     return new_obj
> ```
>
> ### 5.3 Properties
>
> Advantages:
>
> - allocation is extremely fast,
> - no fragmentation,
> - cost is proportional to live data rather than total heap size.
>
> Disadvantages:
>
> - requires extra memory for semispaces,
> - moving objects complicates interoperability with foreign code and raw pointers.
>
> ---
>
> ## 6. Generational Collection
>
> Most programs exhibit the empirical property that most objects die young. A **generational collector** exploits this.
>
> ### 6.1 Generations
>
> Partition objects by age:
>
> - **young generation**
> - **old generation**
>
> New objects are allocated in the young generation. Minor collections scan only the young generation. Surviving objects are promoted to the old generation after one or more collections.
>
> ### 6.2 Why This Helps
>
> If most young objects are dead, then minor collection is cheap because it examines a small region and copies or marks only the few survivors.
>
> ### 6.3 The Write Barrier
>
> A key problem arises when an old object points to a young object. During a minor collection, the young object must still be treated as reachable even if the old object is not scanned completely.
>
> To solve this, the runtime uses a **write barrier** on pointer stores. When storing a reference from object $A$ to object $B$:
>
> - if $A$ is old and $B$ is young,
> - record $A$ in a remembered set or mark the corresponding card dirty.
>
> Example barrier:
>
> ```text
> store(A.field, B):
>     A.field = B
>     if is_old(A) and is_young(B):
>         remember(A)
> ```
>
> Then a minor collection scans:
>
> - roots,
> - remembered old-to-young references,
> - young objects reachable from them.
>
> ### 6.4 Common Design
>
> A practical collector often combines:
>
> - copying collection for the young generation,
> - mark-sweep or mark-compact for the old generation.
>
> This is a standard high-performance architecture.
>
> ---
>
> ## 7. Root Scanning
>
> Root identification is one of the most important implementation details.
>
> ### 7.1 Stack Scanning
>
> The collector must inspect each thread’s stack to find live references. There are two main approaches.
>
> #### Precise collection
>
> The compiler emits metadata indicating exactly which stack slots and registers contain pointers at each safe point.
>
> Advantages:
>
> - no false positives,
> - objects can be moved safely.
>
> #### Conservative collection
>
> The collector treats any machine word that looks like a heap address as a possible pointer.
>
> Advantages:
>
> - easier to retrofit into existing systems.
>
> Disadvantages:
>
> - may keep garbage alive accidentally,
> - prevents some moving collector designs.
>
> ### 7.2 Global and Static Data
>
> Global variables and runtime-managed handles must also be enumerated as roots.
>
> ### 7.3 Registers
>
> At a stop-the-world safe point, register contents must be captured and scanned according to compiler metadata.
>
> ---
>
> ## 8. Safe Points and Pausing the Program
>
> A collector must observe the heap in a consistent state. The simplest approach is **stop-the-world collection**:
>
> 1. pause all mutator threads,
> 2. scan roots,
> 3. collect,
> 4. resume execution.
>
> To make this safe, compiled code inserts **safe points** at locations such as:
>
> - function calls,
> - loop back edges,
> - allocation sites.
>
> At a safe point, the runtime knows how to enumerate roots correctly.
>
> ---
>
> ## 9. Handling Object Movement
>
> If the collector moves objects, all references must remain valid.
>
> Techniques include:
>
> - updating all roots and object fields during collection,
> - using handles instead of direct pointers,
> - pinning some objects so they cannot move.
>
> Pinning is necessary for:
>
> - interfacing with foreign libraries,
> - direct memory I/O,
> - system calls that require stable addresses.
>
> Excessive pinning, however, reduces the effectiveness of compaction.
>
> ---
>
> ## 10. Finalization and Weak References
>
> Real runtimes often support special reference semantics.
>
> ### 10.1 Finalizers
>
> A finalizer runs before an object is reclaimed. This is difficult to implement correctly because:
>
> - finalizer order is subtle,
> - objects may become reachable again,
> - finalization introduces unpredictability.
>
> For this reason, finalizers should be used sparingly.
>
> ### 10.2 Weak References
>
> A weak reference does not keep an object alive. During collection:
>
> - if the referent is reachable by strong references, preserve it;
> - otherwise clear the weak reference or enqueue it for processing.
>
> Weak references are useful for caches, memoization tables, and canonicalization maps.
>
> ---
>
> ## 11. Concurrency and Incrementality
>
> Stop-the-world collection can cause long pauses. To reduce pause times, more advanced collectors may be:
>
> - **incremental**, doing collector work in small steps interleaved with program execution,
> - **concurrent**, running collector threads alongside mutator threads.
>
> These require additional invariants and barriers.
>
> ### 11.1 Tricolor Abstraction
>
> A standard model is:
>
> - **white**: not yet discovered,
> - **gray**: discovered but not yet scanned,
> - **black**: discovered and fully scanned.
>
> The collector must preserve the invariant that no black object points to a white object, or must compensate when this occurs.
>
> ### 11.2 Barriers
>
> Two common barrier styles are:
>
> - **Dijkstra-style insertion barrier**
> - **Yuasa-style deletion barrier**
>
> These record pointer mutations so concurrent marking remains correct.
>
> Such collectors are significantly more complex and are usually implemented only after a basic stop-the-world collector works reliably.
>
> ---
>
> ## 12. A Practical Implementation Plan
>
> A sensible way to implement a garbage collector for a language runtime is to proceed in stages.
>
> ### Stage 1: Precise stop-the-world mark-and-sweep
>
> Implement:
>
> - heap allocator with object headers,
> - root enumeration,
> - mark traversal,
> - sweep into free lists.
>
> This establishes correctness with minimal conceptual complexity.
>
> ### Stage 2: Add compaction or copying for young objects
>
> Introduce:
>
> - bump-pointer allocation,
> - a nursery or young generation,
> - a minor collector,
> - a write barrier and remembered set.
>
> This greatly improves allocation speed and average collection cost.
>
> ### Stage 3: Add old-generation collection
>
> Use:
>
> - mark-sweep for simplicity, or
> - mark-compact to reduce fragmentation.
>
> ### Stage 4: Optimize pause times
>
> Add:
>
> - parallel marking,
> - incremental marking,
> - concurrent sweeping or concurrent marking.
>
> ---
>
> ## 13. Core Data Structures
>
> A collector typically needs the following runtime structures:
>
> - **heap regions**: memory segments for object allocation,
> - **object headers**: mark bits, size, type descriptor, forwarding pointer,
> - **type descriptors**: identify pointer-containing fields,
> - **free lists** or **bump pointers**,
> - **remembered sets** or **card tables** for generations,
> - **stack maps** for precise root scanning.
>
> For example, a type descriptor might provide:
>
> - object size,
> - offsets of pointer fields,
> - alignment,
> - finalization metadata.
>
> Then scanning an object becomes:
>
> ```text
> scan(obj):
>     desc = obj.type_descriptor
>     for each offset in desc.pointer_offsets:
>         visit(*(obj + offset))
> ```
>
> ---
>
> ## 14. Correctness Conditions
>
> A collector is correct if:
>
> 1. every reachable object is preserved,
> 2. every reclaimed object is unreachable,
> 3. after collection, all pointers in the runtime refer either to valid live objects or to null,
> 4. allocator and collector maintain heap invariants.
>
> For moving collectors, one must additionally ensure:
>
> $$
> \forall \text{ pointer } p,\quad p \text{ is updated to the relocated address of its target.}
> $$
>
> Testing should include:
>
> - cyclic structures,
> - deep graphs,
> - cross-generational references,
> - pinned objects,
> - stack roots,
> - weak references,
> - concurrent mutations if applicable.
>
> ---
>
> ## 15. Recommended Minimal Design
>
> For a new language implementation, a strong practical choice is:
>
> 1. **precise root scanning** using compiler-generated stack maps,
> 2. **young-generation copying collector** with bump allocation,
> 3. **old-generation mark-sweep or mark-compact collector**,
> 4. **write barrier** with a remembered set,
> 5. **stop-the-world safe points** initially.
>
> This design balances:
>
> - implementation complexity,
> - performance,
> - fragmentation control,
> - extensibility.
>
> ---
>
> ## Final Answer
>
> To implement a garbage collector, model heap objects as a graph rooted at stacks, globals, and registers; then reclaim objects not reachable from those roots. A clean implementation path is:
>
> 1. build a managed heap with object headers and type descriptors,
> 2. implement precise root scanning,
> 3. start with a stop-the-world **mark-and-sweep** collector,
> 4. add **compaction** or, better, a **copying nursery** for fast allocation,
> 5. make it **generational** using a **write barrier** and remembered set,
> 6. later add parallel, incremental, or concurrent features if pause times matter.
>
> In practice, the most effective baseline design is a **generational collector** with:
>
> - **bump-pointer allocation** in a young generation,
> - **copying collection** for young objects,
> - **mark-sweep or mark-compact** for old objects,
> - **precise stack maps** for root discovery,
> - **safe points** for stop-the-world synchronization.
>
> This architecture is widely used because it is correct, efficient, and extensible.
