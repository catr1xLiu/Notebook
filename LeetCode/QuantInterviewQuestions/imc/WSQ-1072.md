> [!example] Question 1072 · IMC
> ## Software Engineer Interview

Describe the data structures and algorithms needed for a program that keeps track of checked out books for a library. The program should: 1. Check out books for a member with a library card, 2. Return books, 3. Find all books that are overdue and who has them checked out, 4. Find all books that are due tomorrow. Note: New releases and popular books have shorter checkout periods than normal books.

[Source](https://www.thewallstreetquants.com/ebook#p=1073)

> [!success]- Solution (Click to expand)
> ## Solution
>
> A suitable design is to model the library as a set of entities and maintain indexes that support the required operations efficiently.
>
> ---
>
> ## 1. Core Data Structures
>
> ### 1.1 Book Record
>
> Each book should store:
>
> - a unique identifier, such as $bookId$
> - title and author information
> - category, such as:
>   - $Normal$
>   - $NewRelease$
>   - $Popular$
> - status:
>   - $Available$
>   - $CheckedOut$
> - current borrower, if checked out
> - checkout date
> - due date
>
> A record may be represented as:
>
> $$
> Book = (bookId, title, author, category, status, memberId, checkoutDate, dueDate)
> $$
>
> ### 1.2 Member Record
>
> Each member should store:
>
> - unique library card number $memberId$
> - member name
> - contact information
> - list or set of currently checked out books
>
> Representation:
>
> $$
> Member = (memberId, name, contactInfo, checkedOutBooks)
> $$
>
> ### 1.3 Checkout Policy Table
>
> Because checkout periods differ by category, maintain a mapping from category to allowed loan period:
>
> $$
> loanPeriod[Normal] = 14 \text{ days}
> $$
>
> $$
> loanPeriod[NewRelease] = 3 \text{ days}
> $$
>
> $$
> loanPeriod[Popular] = 7 \text{ days}
> $$
>
> The exact values are configurable.
>
> ---
>
> ## 2. Indexes Needed
>
> To perform operations efficiently, use the following structures.
>
> ### 2.1 Hash Table for Books
>
> Maintain a hash table:
>
> $$
> booksById : bookId \to Book
> $$
>
> This supports fast lookup of a book for checkout and return, typically in $O(1)$ average time.
>
> ### 2.2 Hash Table for Members
>
> Maintain a hash table:
>
> $$
> membersById : memberId \to Member
> $$
>
> This supports fast validation of a library card and retrieval of a member record, also typically in $O(1)$ average time.
>
> ### 2.3 Due-Date Index
>
> To find overdue books and books due tomorrow efficiently, maintain an index ordered by due date. A balanced binary search tree or min-heap can be used, but a balanced search tree is more suitable because it supports range queries.
>
> Use:
>
> $$
> dueDateIndex : dueDate \to \{bookId_1, bookId_2, \dots\}
> $$
>
> This can be implemented as a balanced binary search tree, such as a red-black tree or AVL tree.
>
> This structure supports:
>
> - insertion when a book is checked out
> - deletion when a book is returned
> - range query for all books with:
>
> $$
> dueDate < today
> $$
>
> - exact-date query for all books with:
>
> $$
> dueDate = tomorrow
> $$
>
> If the date range is small and discrete, a hash map from date to list of books is also acceptable, but a balanced tree is more general.
>
> ### 2.4 Member’s Checked-Out Set
>
> For each member, maintain a set of checked out book identifiers:
>
> $$
> checkedOutBooks = \{bookId_1, bookId_2, \dots\}
> $$
>
> A hash set is appropriate, allowing insertion and removal in $O(1)$ average time.
>
> ---
>
> ## 3. Main Algorithms
>
> ---
>
> ### 3.1 Check Out a Book
>
> #### Input
> - $memberId$
> - $bookId$
> - $checkoutDate$
>
> #### Steps
>
> 1. Verify that $memberId$ exists in $membersById$.
>    - If not, reject the checkout.
>
> 2. Look up $bookId$ in $booksById$.
>    - If the book does not exist, reject the checkout.
>
> 3. Check whether the book status is $Available$.
>    - If already checked out, reject the checkout.
>
> 4. Determine the loan period from the category:
>
> $$
> period = loanPeriod[book.category]
> $$
>
> 5. Compute the due date:
>
> $$
> dueDate = checkoutDate + period
> $$
>
> 6. Update the book record:
>    - set status to $CheckedOut$
>    - set memberId
>    - set checkoutDate
>    - set dueDate
>
> 7. Add $bookId$ to the member’s $checkedOutBooks$ set.
>
> 8. Insert the book into $dueDateIndex$ under its due date.
>
> #### Time Complexity
>
> - Hash table lookups: $O(1)$ average
> - Tree insertion: $O(\log n)$
>
> Overall:
>
> $$
> O(\log n)
> $$
>
> where $n$ is the number of checked out books.
>
> ---
>
> ### 3.2 Return a Book
>
> #### Input
> - $bookId$
>
> #### Steps
>
> 1. Look up the book in $booksById$.
>    - If not found, reject.
>
> 2. Verify that the book is currently checked out.
>    - If not, reject.
>
> 3. Retrieve the associated $memberId$ and $dueDate$.
>
> 4. Remove $bookId$ from the member’s $checkedOutBooks$ set.
>
> 5. Remove the book from $dueDateIndex$ using its current due date.
>
> 6. Update the book record:
>    - set status to $Available$
>    - clear memberId
>    - clear checkoutDate
>    - clear dueDate
>
> #### Time Complexity
>
> - Hash table operations: $O(1)$ average
> - Tree deletion: $O(\log n)$
>
> Overall:
>
> $$
> O(\log n)
> $$
>
> ---
>
> ### 3.3 Find All Overdue Books and Their Borrowers
>
> #### Input
> - current date $today$
>
> #### Steps
>
> 1. Query the due-date index for all entries with:
>
> $$
> dueDate < today
> $$
>
> 2. For each returned $bookId$, retrieve:
>    - book title
>    - memberId
>    - member name or contact information
>
> 3. Output tuples such as:
>
> $$
> (bookId, title, memberId, memberName, dueDate)
> $$
>
> #### Time Complexity
>
> If $k$ books are overdue, a balanced tree range query takes:
>
> $$
> O(\log n + k)
> $$
>
> This is more efficient than scanning all books, which would take $O(m)$ where $m$ is the total number of books.
>
> ---
>
> ### 3.4 Find All Books Due Tomorrow
>
> #### Input
> - current date $today$
>
> #### Steps
>
> 1. Compute:
>
> $$
> tomorrow = today + 1 \text{ day}
> $$
>
> 2. Query the due-date index for all entries with:
>
> $$
> dueDate = tomorrow
> $$
>
> 3. For each book, retrieve borrower information from the book record and member table.
>
> 4. Output tuples such as:
>
> $$
> (bookId, title, memberId, memberName, dueDate)
> $$
>
> #### Time Complexity
>
> If $k$ books are due tomorrow:
>
> $$
> O(\log n + k)
> $$
>
> ---
>
> ## 4. Why These Structures Are Appropriate
>
> ### Hash Tables
> Hash tables are ideal for direct lookup by identifiers such as $bookId$ and $memberId$. Since checkout and return both begin by finding a specific member and book, these operations should be constant time on average.
>
> ### Balanced Search Tree on Due Dates
> The due-date queries are date-based, not identifier-based. A sorted structure is necessary for efficient retrieval of:
>
> - all books before a date
> - all books on a date
>
> A balanced search tree supports both efficiently.
>
> ### Sets per Member
> A member may have multiple books checked out. A set allows quick insertion and removal and can also support listing everything a member currently has.
>
> ---
>
> ## 5. Alternative Design
>
> Another reasonable design is to store each checkout as a separate transaction record:
>
> $$
> Checkout = (bookId, memberId, checkoutDate, dueDate, returned)
> $$
>
> Then maintain:
>
> - a hash map from $bookId$ to active checkout
> - a balanced tree keyed by $dueDate$ for active checkouts
> - a member-to-active-checkouts map
>
> This is useful if the system must preserve checkout history. In contrast, storing current checkout state directly in the $Book$ record is simpler if only active loans matter.
>
> ---
>
> ## 6. Additional Considerations
>
> A practical library system may also include:
>
> - maximum number of books per member
> - fines for overdue books
> - holds or reservations
> - renewal rules
> - prevention of checkout if a member has unpaid fines
> - separate copies of the same title, each with its own $bookId$
>
> If multiple copies exist, each physical copy should be tracked separately.
>
> ---
>
> ## 7. Final Design Summary
>
> Use:
>
> - a hash table $booksById$ for books
> - a hash table $membersById$ for members
> - a balanced binary search tree $dueDateIndex$ keyed by due date
> - a hash set of checked out books in each member record
> - a category-to-loan-period policy table
>
> This supports:
>
> 1. **Check out books for a valid member**  
>    by validating the member, validating book availability, computing due date from category, and updating all indexes.
>
> 2. **Return books**  
>    by clearing the checkout state and removing the book from the due-date index and the member’s set.
>
> 3. **Find all overdue books and who has them**  
>    by querying all entries with $dueDate < today$.
>
> 4. **Find all books due tomorrow**  
>    by querying all entries with $dueDate = today + 1$.
>
> The resulting operation costs are:
>
> - checkout: $O(\log n)$
> - return: $O(\log n)$
> - overdue query: $O(\log n + k)$
> - due-tomorrow query: $O(\log n + k)$
>
> where $n$ is the number of active checkouts and $k$ is the number of matching results.
