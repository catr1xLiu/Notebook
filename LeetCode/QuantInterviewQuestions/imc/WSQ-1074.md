> [!example] Question 1074 · IMC
> ## Software Engineer Interview

Is an immutable object always thread safe? Explain your reasoning.

[Source](https://www.thewallstreetquants.com/ebook#p=1075)

> [!success]- Solution (Click to expand)
> No. **Immutability often implies thread safety, but not always in every practical sense.**
>
> ## Key idea
>
> An object is *immutable* if its state cannot change after construction.  
> If no thread can modify the object, then concurrent reads do not create race conditions on that state.
>
> So, under the usual definition:
>
> - **properly immutable objects are thread-safe for reading**
> - but **not every object called “immutable” is automatically safe in all multithreaded situations**
>
> ## When an immutable object is thread-safe
>
> An object is thread-safe if multiple threads can use it without causing incorrect behavior.
>
> A truly immutable object is thread-safe when:
>
> 1. all its fields are fixed after construction,
> 2. it does not expose mutable internal state,
> 3. construction is safely published to other threads.
>
> Example of a properly immutable object:
>
> ```java
> final class Point {
>     private final int x;
>     private final int y;
>
>     Point(int x, int y) {
>         this.x = x;
>         this.y = y;
>     }
>
>     int getX() { return x; }
>     int getY() { return y; }
> }
> ```
>
> Since $x$ and $y$ never change, concurrent access is safe.
>
> ## Why the answer is not simply “always yes”
>
> ### 1. The object may look immutable but contain mutable state
>
> ```java
> final class Person {
>     private final List<String> names;
>
>     Person(List<String> names) {
>         this.names = names;
>     }
>
>     List<String> getNames() {
>         return names;
>     }
> }
> ```
>
> Here the reference $names$ is final, but the list itself may still be modified.  
> So the object is **not deeply immutable**, and thus not truly thread-safe.
>
> ### 2. Unsafe publication
>
> Even if an object is immutable after construction, if it is shared between threads incorrectly, another thread may observe it in an improperly initialized state in some languages or memory models.
>
> Thus, immutability alone is not enough; **safe publication** matters.
>
> ### 3. Methods may have side effects outside the object
>
> An object’s fields may be immutable, but its methods could still interact with external mutable state, caches, files, or global variables. Then the object as a whole may not behave thread-safely.
>
> ## Correct conclusion
>
> - **A properly constructed, deeply immutable, safely published object is thread-safe.**
> - **But an object that is only superficially immutable is not necessarily thread-safe.**
>
> Therefore, the statement
>
> $$
> \text{“immutable object is always thread-safe”}
> $$
>
> is **not universally true** without qualification.
>
> ## Final answer
>
> **No.** A *properly* immutable object is generally thread-safe, but an object that merely appears immutable may still be unsafe if it exposes mutable internals, depends on mutable external state, or is not safely published across threads.
