> ## Software Engineering Intern Interview

What is a pointer and a shared pointer? How do you manage object ownership using these in programming?

[Source](https://www.thewallstreetquants.com/ebook#p=1098)

> [!success]- Solution (Click to expand)
> ## Pointers, Shared Pointers, and Object Ownership
>
> ### 1. Pointer
>
> A **pointer** is an object that stores the memory address of another object.
>
> For example, in C++:
>
> ```cpp
> int x = 10;
> int* p = &x;
> ```
>
> Here:
>
> - `x` is an integer.
> - `&x` is the address of `x`.
> - `p` is a pointer to `int`, and it holds the address of `x`.
>
> The expression `*p` dereferences the pointer, meaning it accesses the object pointed to by `p`.
>
> ```cpp
> *p = 20;   // x becomes 20
> ```
>
> Pointers are useful for:
>
> - indirect access to objects,
> - dynamic memory management,
> - passing large objects efficiently,
> - implementing data structures such as linked lists and trees.
>
> However, raw pointers do **not** automatically manage the lifetime of the object they point to.
>
> ---
>
> ### 2. Raw Pointer Ownership
>
> A raw pointer such as `T*` may or may not own the object it points to. This is the source of much confusion.
>
> Example:
>
> ```cpp
> int* p = new int(5);
> ```
>
> Here, `p` points to dynamically allocated memory. Since `new` was used, that memory must later be released:
>
> ```cpp
> delete p;
> ```
>
> If `delete` is forgotten, a **memory leak** occurs.
>
> If `delete` is called twice, **undefined behavior** occurs.
>
> If the object is deleted while some pointer still refers to it, that pointer becomes a **dangling pointer**.
>
> Thus, raw pointers are poor tools for expressing ownership.
>
> ---
>
> ### 3. Object Ownership
>
> **Ownership** answers the question:
>
> Which part of the program is responsible for destroying the object?
>
> There are several common ownership models:
>
> - **Exclusive ownership**: exactly one owner is responsible for destruction.
> - **Shared ownership**: multiple owners share responsibility.
> - **Non-owning access**: an object is referenced, but not owned.
>
> Good software design makes ownership explicit.
>
> ---
>
> ### 4. Smart Pointers
>
> C++ provides **smart pointers** to manage ownership safely.
>
> The main ones are:
>
> - `std::unique_ptr<T>` for exclusive ownership,
> - `std::shared_ptr<T>` for shared ownership,
> - `std::weak_ptr<T>` for non-owning observation of a shared object.
>
> ---
>
> ## 5. `std::shared_ptr`
>
> A `std::shared_ptr<T>` is a smart pointer that implements **shared ownership**.
>
> Multiple `shared_ptr` objects can point to the same object. The object is destroyed automatically when the last owning `shared_ptr` is destroyed or reset.
>
> Example:
>
> ```cpp
> #include <memory>
>
> std::shared_ptr<int> p1 = std::make_shared<int>(42);
> std::shared_ptr<int> p2 = p1;   // shared ownership
> ```
>
> Now both `p1` and `p2` own the same integer.
>
> The number of owners is tracked by a **reference count**:
>
> ```cpp
> p1.use_count();   // typically 2 here
> ```
>
> When one owner goes away:
>
> ```cpp
> p1.reset();
> ```
>
> the object is not destroyed yet, because `p2` still owns it.
>
> When the last owner disappears, the object is deleted automatically.
>
> ---
>
> ### 6. How `shared_ptr` Works
>
> A `shared_ptr` usually maintains:
>
> - a pointer to the managed object,
> - a pointer to a **control block**.
>
> The control block stores:
>
> - the reference count for shared owners,
> - the weak reference count,
> - possibly a custom deleter,
> - allocator-related data.
>
> When a `shared_ptr` is copied, the shared count is incremented.
>
> When a `shared_ptr` is destroyed, the shared count is decremented.
>
> If the shared count becomes $0$, the managed object is destroyed.
>
> If both the shared count and weak count become $0$, the control block is deallocated.
>
> ---
>
> ## 7. `std::unique_ptr` versus `std::shared_ptr`
>
> ### `std::unique_ptr<T>`
>
> Use `unique_ptr` when exactly one object owns the resource.
>
> ```cpp
> std::unique_ptr<int> p = std::make_unique<int>(42);
> ```
>
> Properties:
>
> - cannot be copied,
> - can be moved,
> - has very low overhead,
> - expresses exclusive ownership clearly.
>
> ### `std::shared_ptr<T>`
>
> Use `shared_ptr` when multiple parts of the program genuinely need co-ownership.
>
> ```cpp
> std::shared_ptr<int> p = std::make_shared<int>(42);
> ```
>
> Properties:
>
> - can be copied,
> - uses reference counting,
> - has more overhead than `unique_ptr`,
> - can lead to cycles if used carelessly.
>
> In general, prefer `unique_ptr` unless shared ownership is truly needed.
>
> ---
>
> ## 8. Non-Owning Pointers
>
> Sometimes a function or object needs access to another object without taking ownership.
>
> Then use:
>
> - a raw pointer `T*`, or
> - a reference `T&`, if null is not allowed.
>
> Example:
>
> ```cpp
> void print(const std::string* s);
> void update(std::string& s);
> ```
>
> Interpretation:
>
> - `std::string*` may be null and does not imply ownership.
> - `std::string&` must refer to a valid object and does not imply ownership.
>
> Raw pointers are best used as **non-owning** pointers.
>
> ---
>
> ## 9. Managing Ownership Correctly
>
> ### Rule 1: Prefer automatic storage when possible
>
> ```cpp
> Widget w;
> ```
>
> This is simplest and safest. The object is destroyed automatically when it goes out of scope.
>
> ---
>
> ### Rule 2: Use `std::unique_ptr` for exclusive ownership
>
> ```cpp
> auto w = std::make_unique<Widget>();
> ```
>
> This clearly expresses that one object owns `w`.
>
> ---
>
> ### Rule 3: Use `std::shared_ptr` only for true shared ownership
>
> ```cpp
> auto w = std::make_shared<Widget>();
> ```
>
> Use this only when multiple objects must extend the lifetime of `w`.
>
> ---
>
> ### Rule 4: Use raw pointers or references for non-owning access
>
> ```cpp
> void f(Widget* w);   // non-owning, nullable
> void g(Widget& w);   // non-owning, non-null
> ```
>
> Do not use raw pointers to represent ownership unless there is a strong reason and lifetime is carefully controlled.
>
> ---
>
> ### Rule 5: Avoid manual `new` and `delete`
>
> Instead of:
>
> ```cpp
> Widget* w = new Widget;
> // ...
> delete w;
> ```
>
> prefer:
>
> ```cpp
> auto w = std::make_unique<Widget>();
> ```
>
> or
>
> ```cpp
> auto w = std::make_shared<Widget>();
> ```
>
> This prevents leaks and makes ownership explicit.
>
> ---
>
> ## 10. Common Problems with `shared_ptr`
>
> ### Circular References
>
> If two objects hold `shared_ptr` to each other, neither reference count reaches $0$.
>
> Example:
>
> ```cpp
> struct B;
>
> struct A {
>     std::shared_ptr<B> b;
> };
>
> struct B {
>     std::shared_ptr<A> a;
> };
> ```
>
> This creates a cycle, causing a memory leak.
>
> ### Solution: `std::weak_ptr`
>
> Replace one side with `weak_ptr`:
>
> ```cpp
> struct B;
>
> struct A {
>     std::shared_ptr<B> b;
> };
>
> struct B {
>     std::weak_ptr<A> a;
> };
> ```
>
> A `weak_ptr` does not contribute to ownership. It can observe an object managed by `shared_ptr` without extending its lifetime.
>
> To access the object safely:
>
> ```cpp
> if (auto sp = a.lock()) {
>     // use *sp
> }
> ```
>
> If the object has already been destroyed, `lock()` returns an empty `shared_ptr`.
>
> ---
>
> ## 11. Practical Ownership Guidelines
>
> A useful decision process is:
>
> 1. **Can the object live on the stack?**  
>    Use automatic storage.
>
> 2. **Does exactly one part of the program own it?**  
>    Use `std::unique_ptr`.
>
> 3. **Do several parts need to co-own it?**  
>    Use `std::shared_ptr`.
>
> 4. **Does something merely observe it?**  
>    Use `T*`, `T&`, or `std::weak_ptr` if the object is managed by `shared_ptr`.
>
> ---
>
> ## 12. Example
>
> ```cpp
> #include <iostream>
> #include <memory>
>
> class Engine {
> public:
>     void start() {
>         std::cout << "Engine started\n";
>     }
> };
>
> class Car {
> private:
>     std::unique_ptr<Engine> engine;
> public:
>     Car() : engine(std::make_unique<Engine>()) {}
>
>     Engine* getEngine() {
>         return engine.get();   // non-owning access
>     }
> };
> ```
>
> Here:
>
> - `Car` has exclusive ownership of `Engine` through `std::unique_ptr<Engine>`.
> - `getEngine()` returns a raw pointer for non-owning access.
> - The `Engine` is destroyed automatically when the `Car` is destroyed.
>
> If many cars or systems needed to co-own the same `Engine`, then `std::shared_ptr<Engine>` might be appropriate, but that is less common.
>
> ---
>
> ## 13. Summary
>
> - A **pointer** stores the address of another object.
> - A raw pointer `T*` does **not** automatically manage lifetime.
> - **Ownership** means responsibility for destroying an object.
> - Use:
>   - `std::unique_ptr` for exclusive ownership,
>   - `std::shared_ptr` for shared ownership,
>   - `std::weak_ptr` to observe a shared object without owning it,
>   - raw pointers or references for non-owning access.
> - Prefer clear ownership rules and avoid manual `new`/`delete`.
> - Prefer `std::unique_ptr` by default; use `std::shared_ptr` only when shared lifetime is truly required.
