> ## Intern Interview

What are hashmaps, and how are they implemented?

[Source](https://www.thewallstreetquants.com/ebook#p=1052)

> [!success]- Solution (Click to expand)
> ## Hashmaps
>
> A **hashmap** is a data structure that stores **key–value pairs** and supports fast operations such as:
>
> - **insert** a pair $(k, v)$,
> - **lookup** the value associated with a key $k$,
> - **delete** a key $k$.
>
> Its goal is to make these operations run in approximately constant time, typically $O(1)$ on average.
>
> For example, a hashmap might store:
>
> - `"name" \mapsto "Alice"`
> - `"age" \mapsto 25`
>
> Given the key `"name"`, the hashmap returns `"Alice"`.
>
> ---
>
> ## Basic idea
>
> A hashmap uses a **hash function** $h(k)$ to convert a key $k$ into an integer, which is then used as an index into an array.
>
> If the underlying array has size $m$, the index is often computed as
>
> $$
> \text{index} = h(k) \bmod m.
> $$
>
> Thus, instead of searching through all stored keys, the structure jumps directly to a likely location.
>
> ---
>
> ## Why hashing helps
>
> Suppose keys are strings, integers, or other objects. A hash function maps each key to a number in a way that is:
>
> - fast to compute,
> - deterministic: the same key always gives the same hash,
> - intended to spread keys uniformly across the array.
>
> If keys are well distributed, operations are very fast on average.
>
> ---
>
> ## Main components of a hashmap
>
> A hashmap typically consists of:
>
> 1. **An array of buckets** of size $m$.
> 2. **A hash function** $h(k)$.
> 3. **A collision-resolution strategy**, since different keys may map to the same bucket.
>
> A **collision** occurs when two distinct keys $k_1 \neq k_2$ satisfy
>
> $$
> h(k_1) \bmod m = h(k_2) \bmod m.
> $$
>
> Since the number of possible keys is usually much larger than the number of buckets, collisions are unavoidable.
>
> ---
>
> ## Collision resolution
>
> There are two standard implementation strategies.
>
> ### 1. Separate chaining
>
> In **separate chaining**, each array entry stores a collection of key–value pairs, often a linked list or dynamic array.
>
> If multiple keys hash to the same index, they are stored in that bucket’s chain.
>
> ### Structure
>
> $$
> \text{table}[i] \rightarrow [(k_1, v_1), (k_2, v_2), \dots]
> $$
>
> ### Operations
>
> #### Lookup
>
> To find key $k$:
>
> 1. Compute $i = h(k) \bmod m$.
> 2. Go to bucket $i$.
> 3. Search through the bucket for key $k$.
>
> #### Insert
>
> 1. Compute $i = h(k) \bmod m$.
> 2. Search bucket $i$ for $k$.
> 3. If found, update its value.
> 4. Otherwise, add $(k, v)$ to the bucket.
>
> #### Delete
>
> 1. Compute $i = h(k) \bmod m$.
> 2. Search bucket $i$.
> 3. Remove the pair if present.
>
> ### Time complexity
>
> If the hash function distributes keys well, the expected bucket length is small. Let
>
> $$
> \alpha = \frac{n}{m}
> $$
>
> be the **load factor**, where $n$ is the number of stored entries and $m$ is the number of buckets.
>
> Then the average cost of lookup, insert, and delete is approximately
>
> $$
> O(1 + \alpha).
> $$
>
> If $\alpha$ is kept bounded, this is $O(1)$ on average.
>
> In the worst case, all keys could land in one bucket, giving
>
> $$
> O(n).
> $$
>
> ---
>
> ### 2. Open addressing
>
> In **open addressing**, all entries are stored directly inside the array. If a collision occurs, the structure probes other slots according to a rule.
>
> Common probing methods include:
>
> - **Linear probing**
> - **Quadratic probing**
> - **Double hashing**
>
> ### Linear probing
>
> If a key hashes to index $i$ and that slot is occupied, check:
>
> $$
> i, i+1, i+2, \dots
> $$
>
> wrapping around modulo $m$ until an empty slot or the key is found.
>
> More formally, probe sequence:
>
> $$
> (h(k) + j) \bmod m, \quad j = 0, 1, 2, \dots
> $$
>
> ### Operations
>
> #### Lookup
>
> Probe according to the sequence until:
>
> - the key is found, or
> - an empty slot is reached, meaning the key is absent.
>
> #### Insert
>
> Probe until an empty slot is found, then place the entry there.
>
> #### Delete
>
> Deletion is more delicate. A removed entry cannot simply become empty, because that might break probe chains. Instead, many implementations mark the slot with a special **deleted** marker.
>
> ### Time complexity
>
> For a low load factor, operations are $O(1)$ on average. But performance degrades as the table becomes full.
>
> Worst-case time is again
>
> $$
> O(n).
> $$
>
> ---
>
> ## Resizing and rehashing
>
> As more elements are inserted, the load factor
>
> $$
> \alpha = \frac{n}{m}
> $$
>
> increases, and collisions become more frequent.
>
> To maintain efficiency, hashmaps usually **resize** when $\alpha$ exceeds a threshold, such as $0.75$.
>
> ### Rehashing process
>
> 1. Allocate a larger array, often with size about $2m$.
> 2. Recompute positions for all existing keys.
> 3. Insert them into the new table.
>
> This process is called **rehashing**, because indices depend on the table size.
>
> Although one resize operation may cost $O(n)$, it happens only occasionally, so insertion remains $O(1)$ **amortized**.
>
> ---
>
> ## Properties of a good hash function
>
> A good hash function should:
>
> - be fast,
> - distribute keys evenly,
> - minimize collisions,
> - depend on all parts of the key.
>
> For integers, one may use arithmetic transformations. For strings, implementations often combine character codes using multiplication and addition.
>
> In practice, language runtimes usually provide built-in hash functions for standard types.
>
> ---
>
> ## Example
>
> Suppose the table size is $m = 5$, and the hash function is
>
> $$
> h(k) = k.
> $$
>
> Then the index is $k \bmod 5$.
>
> Insert keys $12$, $7$, and $22$:
>
> - $12 \bmod 5 = 2$
> - $7 \bmod 5 = 2$
> - $22 \bmod 5 = 2$
>
> All three keys map to bucket $2$, so a collision occurs.
>
> ### With separate chaining
>
> Bucket $2$ contains
>
> $$
> [(12, v_1), (7, v_2), (22, v_3)].
> $$
>
> ### With open addressing
>
> - Place $12$ at slot $2$.
> - $7$ collides, so try the next slot.
> - $22$ collides again and continues probing until a free slot is found.
>
> ---
>
> ## Average-case versus worst-case performance
>
> Hashmaps are popular because their **average-case** performance is excellent:
>
> - insert: $O(1)$
> - lookup: $O(1)$
> - delete: $O(1)$
>
> However, the **worst case** can be
>
> $$
> O(n),
> $$
>
> especially if many collisions occur.
>
> Thus, performance depends on:
>
> - the quality of the hash function,
> - the collision-resolution method,
> - the load factor,
> - resizing policy.
>
> ---
>
> ## Comparison with other structures
>
> - A **balanced binary search tree** supports operations in $O(\log n)$ worst-case time and keeps keys ordered.
> - A **hashmap** usually gives $O(1)$ average time, but does **not** maintain keys in sorted order.
>
> So hashmaps are ideal when fast key-based access matters more than ordering.
>
> ---
>
> ## Summary
>
> A hashmap is a key–value data structure implemented using:
>
> - an array,
> - a hash function that maps keys to array positions,
> - a method for handling collisions.
>
> The two main implementations are:
>
> 1. **Separate chaining**: each bucket stores a list of entries.
> 2. **Open addressing**: entries are stored directly in the array and collisions are resolved by probing.
>
> With a good hash function and controlled load factor, hashmaps provide $O(1)$ average-time insert, lookup, and delete, which is why they are widely used in programming languages and systems.
