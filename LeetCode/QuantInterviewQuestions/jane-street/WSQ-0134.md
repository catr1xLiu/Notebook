> [!example] Question 134 · Jane Street
> ## Intern Interview

Design a real-time system to process millions of trades per second. How would you ensure low latency, fault tolerance, and exactly-once processing?

[Source](https://www.thewallstreetquants.com/ebook#p=135)

> [!success]- Solution (Click to expand)
> ## Approach
>
> To process millions of trades per second in real time, the system must balance three goals:
>
> 1. **Low latency**: end-to-end processing in milliseconds or below.
> 2. **Fault tolerance**: no data loss despite machine, process, or network failures.
> 3. **Exactly-once processing**: each trade affects downstream state and outputs exactly once, even under retries and failover.
>
> A practical design is an event-driven, partitioned streaming architecture with durable logs, stateful stream processors, replicated state, and transactional writes.
>
> ---
>
> ## 1. High-Level Architecture
>
> A suitable architecture consists of the following layers:
>
> ### Ingestion Layer
> - Market gateways, order routers, or upstream trading systems publish trade events.
> - Events are appended to a **durable distributed log** partitioned by key, such as:
>   - instrument ID,
>   - account ID,
>   - venue,
>   - or trade ID hash.
>
> This log must support:
> - sequential appends,
> - replication,
> - ordered delivery within a partition,
> - consumer offsets.
>
> ### Stream Processing Layer
> A cluster of stateless and stateful processors consumes the log and performs:
> - validation,
> - enrichment,
> - deduplication,
> - risk checks,
> - aggregation,
> - routing to downstream systems.
>
> The processors should be partition-aware so each partition is handled by one active task at a time.
>
> ### State Store Layer
> For stateful computation, processors maintain:
> - local embedded state for speed,
> - backed by a changelog in the durable log for recovery.
>
> Examples of state:
> - seen-trade IDs for deduplication,
> - per-account exposure,
> - per-instrument aggregates,
> - sliding-window metrics.
>
> ### Output Layer
> Results are written to:
> - downstream topics,
> - operational databases,
> - risk engines,
> - real-time dashboards,
> - settlement systems.
>
> Exactly-once output requires transactional or idempotent sinks.
>
> ---
>
> ## 2. Ensuring Low Latency
>
> Low latency is achieved by minimizing coordination, minimizing random I/O, and preserving locality.
>
> ### 2.1 Partitioning for Parallelism
> The system must shard the stream across many partitions.
>
> If the incoming rate is $R$ trades per second and a single processing task handles $r$ trades per second, then the number of required active partitions is approximately
>
> $$
> P \ge \left\lceil \frac{R}{r} \right\rceil .
> $$
>
> For millions of trades per second, this usually implies hundreds or thousands of partitions.
>
> Partitioning principles:
> - Use a key that preserves required ordering.
> - Avoid hot partitions by choosing a high-cardinality key.
> - If ordering is needed per instrument, partition by instrument.
> - If ordering is needed per account, partition by account.
>
> ### 2.2 Sequential Log Writes
> A distributed append-only log is preferred because:
> - disk and network are used in large sequential batches,
> - consumers read sequentially,
> - writes can be replicated efficiently.
>
> This is substantially faster than per-record random database writes.
>
> ### 2.3 Local Stateful Processing
> State should be kept close to compute:
> - in-memory for hottest working sets,
> - local persistent storage for durability and fast recovery.
>
> Remote database round-trips on every trade would destroy latency.
>
> ### 2.4 Batching Without Violating Latency Targets
> Micro-batching at the transport or replication level can improve throughput while keeping end-to-end latency low. For example:
> - batch network sends for a few hundred microseconds,
> - flush producer buffers frequently,
> - process records one by one logically, but commit offsets and state changes in tiny batches.
>
> ### 2.5 Avoid Synchronous Cross-Service Calls
> The critical trade path should not depend on synchronous calls to external systems unless absolutely necessary. Instead:
> - preload reference data in memory,
> - replicate static metadata locally,
> - emit asynchronous side effects.
>
> ### 2.6 CPU and Memory Efficiency
> Low latency also requires:
> - binary message formats,
> - zero-copy or low-copy serialization,
> - preallocated object pools where appropriate,
> - minimizing garbage collection pauses,
> - NUMA-aware deployment for extreme throughput,
> - pinning hot threads to CPU cores when needed.
>
> ### 2.7 Network Design
> Use:
> - high-bandwidth, low-latency networking,
> - colocated processing and brokers when possible,
> - compression only if CPU cost is justified,
> - separate networks for replication and client traffic in large clusters.
>

>
> ## 3. Ensuring Fault Tolerance
>
> Fault tolerance requires durability, replication, recovery, and controlled failover.
>
> ### 3.1 Durable Replicated Log
> Every trade event should first be written to a replicated log before being acknowledged.
>
> If a partition has replication factor $f$, then the system can typically tolerate up to $f-1$ replica losses in principle, subject to quorum and leader-election policy.
>
> A common pattern:
> - one leader replica handles writes,
> - followers replicate the log,
> - acknowledgments occur only after replication to a quorum or all in-sync replicas.
>
> This prevents data loss from a single node failure.
>
> ### 3.2 Stateless vs. Stateful Recovery
> - **Stateless processors** can restart and resume consuming from offsets.
> - **Stateful processors** recover by:
>   1. loading the latest local checkpoint or snapshot,
>   2. replaying changelog records from the durable log,
>   3. resuming consumption from the last committed input offset.
>
> ### 3.3 Active-Passive or Shared-Nothing Task Recovery
> Each partitioned processing task should have:
> - one active owner,
> - one or more standby replicas of its state.
>
> Upon failure:
> - a standby is promoted,
> - it continues from the last durable offset,
> - replay fills any gap.
>
> This reduces recovery time dramatically.
>
> ### 3.4 Backpressure
> A fault-tolerant system must degrade gracefully under overload.
>
> Implement backpressure:
> - consumers slow intake when processing or sink layers lag,
> - producers are throttled or buffered,
> - partition lag is monitored.
>
> Without backpressure, overload leads to queue explosion and unacceptable latency.
>
> ### 3.5 Multi-AZ or Multi-Region Deployment
> For high availability:
> - replicate across availability zones,
> - ensure leaders and replicas are not colocated in one failure domain,
> - optionally mirror logs to another region for disaster recovery.
>
> Cross-region synchronous replication increases latency, so a common design is:
> - synchronous replication within one region for low latency,
> - asynchronous replication to a remote region for disaster recovery.
>
> ---
>
> ## 4. Ensuring Exactly-Once Processing
>
> Exactly-once processing is the most subtle requirement. It means that, despite retries and failures, the final effect of processing each trade is as if it were processed once.
>
> This requires careful handling of:
> - duplicate inputs,
> - repeated processing after failover,
> - repeated output writes,
> - atomicity between state updates and offset commits.
>
> ### 4.1 Why At-Least-Once Is Not Enough
> With at-least-once delivery, a processor may:
> 1. read a trade,
> 2. update state,
> 3. crash before committing its offset,
> 4. re-read the same trade after restart.
>
> Without special handling, the trade would be counted twice.
>
> ### 4.2 Core Principle
> Exactly-once is achieved by making the following atomic:
>
> - input consumption position,
> - state update,
> - output publication.
>
> Conceptually, for each processed record or batch, perform one transaction:
>
> $$
> \text{consume input} \;\;+\;\; \text{update state} \;\;+\;\; \text{write output} \;\;+\;\; \text{commit offset}
> $$
>
> all as a single indivisible unit.
>
> ### 4.3 Idempotent Producers
> When writing to the output log, producers should be idempotent:
> - retries from the same producer session do not create duplicate records,
> - sequence numbers or producer epochs prevent duplicates after transient failures.
>
> This solves duplicate writes caused by network retry.
>
> ### 4.4 Transactional Processing
> Use transactions that bind:
> - the output writes,
> - the state changelog writes,
> - the consumer offset commit.
>
> If the transaction commits, all effects are visible.
> If it aborts, none are visible.
>
> Thus after failure:
> - committed work is not repeated incorrectly,
> - uncommitted work is retried safely.
>
> ### 4.5 Deduplication by Trade ID
> Even with transactional processing, business-level deduplication is often necessary because upstream systems may resend the same trade with the same business identifier.
>
> Maintain a deduplication state store keyed by trade ID.
>
> For each incoming trade with ID $t$:
> - if $t$ is absent, process and record $t$,
> - if $t$ is present, discard as duplicate.
>
> Formally, define a set $D$ of processed trade IDs. For incoming trade $t$:
>
> $$
> t \in D \implies \text{drop}
> $$
>
> $$
> t \notin D \implies \text{process and update } D \leftarrow D \cup \{t\}
> $$
>
> This state must itself be part of the exactly-once transaction.
>
> ### 4.6 External Sink Consistency
> Exactly-once is easiest when both source and sink are the same transactional log system. It is harder when writing to external databases or services.
>
> There are three strategies:
>
> #### Strategy A: Transactional Sink
> If the external system supports transactions coordinated with offsets or idempotency keys, use that.
>
> #### Strategy B: Idempotent Upserts
> Write using a unique business key such as trade ID. Repeated writes become harmless.
>
> For example, instead of insert-only:
> - use upsert keyed by trade ID,
> - maintain version or sequence checks.
>
> #### Strategy C: Outbox Pattern
> Write results first to a transactional outbox in the same system as your state, then asynchronously deliver to external systems. Consumers of the outbox use idempotency keys.
>
> This prevents inconsistency between internal state and side effects.
>

> ## 5. Detailed Processing Flow
>
> A robust per-partition flow is as follows.
>
> ### Step 1: Producer Ingests Trade
> The trade producer:
> - assigns a partition key,
> - writes the event to the replicated log,
> - waits for durable acknowledgment.
>
> ### Step 2: Processor Reads from Partition
> The processing task assigned to that partition:
> - polls a batch of trades,
> - processes them in partition order.
>
> ### Step 3: Validate and Enrich
> For each trade:
> - verify schema,
> - check mandatory fields,
> - attach reference data from local caches,
> - reject malformed or stale events.
>
> ### Step 4: Deduplicate
> Consult deduplication state:
> - if trade ID already exists, mark duplicate and do not reapply business effects,
> - otherwise continue.
>
> ### Step 5: Apply Stateful Logic
> Update state such as:
> - net positions,
> - exposure,
> - per-symbol volume,
> - alert thresholds.
>
> ### Step 6: Produce Outputs
> Emit:
> - normalized trade stream,
> - aggregate updates,
> - risk events,
> - audit events.
>
> ### Step 7: Commit Atomically
> Within one transaction:
> - write output records,
> - persist state changes via changelog,
> - commit input offsets.
>
> Then mark the transaction committed.
>
> ---
>
> ## 6. Ordering Considerations
>
> Ordering and exactly-once interact strongly.
>
> ### 6.1 Per-Partition Ordering
> A log guarantees order only within a partition. Therefore, any business rule requiring strict order for a key must ensure all related events land in the same partition.
>
> ### 6.2 Global Ordering
> Global total order across millions of trades per second is usually too expensive and unnecessary. It introduces a throughput bottleneck.
>
> Instead:
> - require order per instrument or per account,
> - use event time and sequence numbers where needed,
> - reconcile across partitions only for aggregate views.
>
> ### 6.3 Late and Out-of-Order Events
> If trade events may arrive out of order:
> - attach event timestamps and source sequence numbers,
> - maintain bounded reordering buffers or watermarks,
> - define business policy for corrections and cancels.
>
> ---
>
> ## 7. State Management and Recovery
>
> ### 7.1 Local State + Changelog
> Each processor stores state locally for speed and appends every state mutation to a replicated changelog.
>
> Recovery procedure:
> 1. restart processor on same or new node,
> 2. restore latest snapshot if available,
> 3. replay changelog,
> 4. resume consuming from committed offsets.
>
> ### 7.2 Snapshots
> To avoid replaying an unbounded history, periodically create snapshots of state.
>
> If replay rate is $c$ records per second and changelog length since the last snapshot is $L$, then restore time is approximately
>
> $$
> T_{\text{restore}} \approx \frac{L}{c}.
> $$
>
> Frequent snapshots reduce recovery time but add overhead. Choose a snapshot interval that meets recovery objectives.
>
> ### 7.3 Standby Replicas
> Maintain warm standbys that continuously apply changelog updates. Then on failover:
> - promotion is quick,
> - replay gap is small,
> - latency spike is minimized.
>
> ---
>
> ## 8. Fault Scenarios and Correctness
>
> ### Case 1: Producer Retries After Timeout
> Suppose the producer sends a trade, the broker stores it, but the acknowledgment is lost. The producer retries.
>
> Solution:
> - use idempotent producer semantics,
> - broker recognizes duplicate sequence number,
> - only one log append is retained.
>
> ### Case 2: Processor Crashes After State Update but Before Offset Commit
> Without transactions, restart causes reprocessing and double application.
>
> Solution:
> - state update and offset commit are in one transaction,
> - if crash occurs before commit, the update is not visible as committed,
> - on restart, the record is reprocessed exactly once.
>
> ### Case 3: Processor Crashes After Output Write but Before Acknowledgment
> Without idempotent or transactional output, duplicate downstream records may appear.
>
> Solution:
> - transactional output or idempotent sink keyed by trade ID.
>
> ### Case 4: Node Loss During High Load
> The partition leader fails.
>
> Solution:
> - replica election promotes an in-sync follower,
> - consumers reconnect,
> - processor tasks rebalance,
> - standby state replicas reduce restore time.
>

>
> ## 9. Operational Design
>
> A real-time trading platform must also be observable and controllable.
>
> ### 9.1 Metrics
> Track:
> - end-to-end latency percentiles such as $p50$, $p95$, $p99$, $p99.9$,
> - consumer lag,
> - partition skew,
> - transaction commit latency,
> - dedup hit rate,
> - state restore time,
> - broker replication lag,
> - dropped or malformed event counts.
>
> ### 9.2 Alerts
> Alert on:
> - rising lag,
> - replication under-minimum replicas,
> - transaction abort spikes,
> - hot partitions,
> - GC pauses,
> - increasing duplicate rate,
> - slow sink writes.
>
> ### 9.3 Capacity Planning
> Let:
> - $R$ be trade rate,
> - $s$ be average event size in bytes,
> - $k$ be replication factor.
>
> Then raw ingress bandwidth is
>
> $$
> B_{\text{ingress}} = R \cdot s.
> $$
>
> Including replication, broker-side write bandwidth is approximately
>
> $$
> B_{\text{broker}} \approx k \cdot R \cdot s.
> $$
>
> This must be provisioned with headroom for bursts, rebalancing, and recovery replay.
>
> ### 9.4 Testing
> Required tests include:
> - failure injection,
> - duplicate replay tests,
> - broker failover tests,
> - partition reassignment under load,
> - network partition scenarios,
> - transactional abort and recovery validation.
>
> Exactly-once guarantees should be verified with deterministic end-state checks.
>
> ---
>
> ## 10. Recommended Design Summary
>
> A strong design for this problem is:
>
> 1. **Replicated partitioned commit log** for ingestion.
> 2. **Partitioned stream processors** for horizontal scale.
> 3. **Local state stores with replicated changelogs** for low-latency stateful operations.
> 4. **Transactional processing** that atomically couples:
>    - consumed offsets,
>    - state updates,
>    - output writes.
> 5. **Idempotent producer semantics** and **business-level deduplication by trade ID**.
> 6. **Standby replicas and snapshots** for fast failover and recovery.
> 7. **Backpressure, monitoring, and hot-partition management** for stable operation.
>
> ---
>
> ## Final Answer
>
> To process millions of trades per second with low latency, fault tolerance, and exactly-once semantics, use a **partitioned streaming architecture built on a replicated append-only log**.
>
> - **Low latency** is achieved by:
>   - sharding trades across many partitions,
>   - processing partitions in parallel,
>   - keeping state local to compute,
>   - using sequential log I/O,
>   - avoiding synchronous remote calls,
>   - and using efficient binary serialization and tight batching.
>
> - **Fault tolerance** is achieved by:
>   - replicating the input log across failure domains,
>   - checkpointing state via changelogs and snapshots,
>   - promoting standby replicas on failure,
>   - and applying backpressure under overload.
>
> - **Exactly-once processing** is achieved by:
>   - idempotent producers,
>   - transactional stream processing,
>   - atomically coupling input offsets, state updates, and output writes,
>   - and maintaining a deduplication store keyed by trade ID.
>
> In short, the core correctness mechanism is:
>
> $$
> \text{read trade} + \text{deduplicate} + \text{update state} + \text{emit outputs} + \text{commit offset}
> $$
>
> performed as **one atomic transaction**, with all durable data replicated and recoverable. This yields a system that is horizontally scalable, resilient to failure, and correct under retries and failover.
